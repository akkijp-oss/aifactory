1. 一言でいうと何か

「エージェント 1 体につき隔離された計算機 1 台」を、自前の Proxmox クラスタのノード 1 台（本文では pve1）上の VM として 常駐プールで用意し、Mac の CLI（sandbox）の 5 操作 take / ssh / url / reset / release で貸し借りする仕組み。VM の中に Claude Code と対象リポジトリのアプリ一式が焼いてあり、タスクが終わったら RAM 込みスナップショット clean に巻き戻して次のタスクに回す。

どこで動く

Proxmox ホスト pve1（数十コア / 200GB 級 RAM）の local-lvm。単一ノード。

何台あるか

ゲートウェイ LXC 1 台、テンプレート（base 1 + PJ ごと 1）、プール VM（PJ ごと 3 + 汎用 3。3 PJ なら 12 台）。全プール running。

どう届く

Mac → Tailscale → ゲートウェイ LXC sb-gw（subnet router）→ 専用網 10.77.0.0/16。名前は task-<id>.sb.internal。

何が毎回消える

VM 内の変更すべて（ファイル・DB・プロセス）と、tmpfs に置いたトークン。テンプレートに焼いたものだけ残る。

3.3 4 本の経路

#誰が → どこへ通り道用途
①Mac → プール VMMac の tailscale → tailnet → sb-gw（tailscale0 → eth1）→ sbnet → VM。戻りは VM → 10.77.0.1（ホスト）ではなく、VM の経路表に sb-gw への戻り経路は無いので、Tailscale が sb-gw で SNAT する（subnet router の既定動作）sandbox ssh、ブラウザで :3000、cmux の surface。到達には route 承認に加えて tailnet の ACL grant に 10.77.0.0/16 が必要だった（STATUS.md）
②Mac → Proxmox ホストLAN の ssh（ホストの ssh エイリアス、root）CLI が qm list / listsnapshot / rollback / start を打つ。VM の生殺与奪はここだけ
③VM → InternetVM → 10.77.0.1 → ホストの iptables で SNAT（送信元 = ホストの LAN アドレス）→ vmbr0 → LAN → 外git push、Claude Code の API 通信、apt / npm。制限なし（allowlist 無し）
④Mac → VM（代替）ssh ProxyJump で Proxmox ホスト経由（ホストが sbnet 上の 10.77.0.1 を持つ）tailnet 未承認・不調時。SB_JUMP=pve1。名前解決が効かないので URL は IP 直打ち

3.4 名前解決の流れ

Mac が task-101.sb.internal を引く
→
Tailscale の split DNS が sb.internal を sb-gw の tailnet アドレスへ
→
sb-gw の dnsmasq（local=/sb.internal/）が /etc/sandbox/hosts を引く
→
10.77.1.13 を返す

/etc/sandbox/hosts は 2 種類の行を持つ。常設名はプール作成時（40-pool.sh）に、task-* 名は sandbox take / release のたびに CLI が ssh で書き換えて systemctl reload dnsmasq する。つまり 「どの VM がどの task か」は Mac の state.json と sb-gw の hosts の 2 箇所にあり、CLI が両方を同時に更新する。

4.2 VM の一生（take / reset / release）

巻き戻しは qm rollback <vmid> clean。RAM 込みなので、巻き戻した瞬間からアプリが :3000 で応答し、cloud-init も走らない。直前の rollback のロックが残ることがあるので CLI は最大 12 回リトライする。

5. データの流れ

5.1 take のとき: 設定とトークンが VM に届くまで

  1. 設定の 3 層を重ねる（後勝ち）: ~/.config/sandbox/env → pj/<pj>.env → 実行時の SANDBOX_CLAUDE_TOKEN / SANDBOX_GH_TOKEN。シェルに export された CLAUDE_CODE_OAUTH_TOKEN / GH_TOKEN は 無視する（PJ 設定を黙って上書きした事故があった。ADR-0006）
  2. GitHub トークンを払い出す（ADR-0008）: Mac の秘密鍵で JWT（RS256、10 分）を作る → GET /repos/{GH_REPO}/installation で installation id → POST /app/installations/{id}/access_tokens（対象リポジトリ 1 つ、contents / pull_requests write、metadata read）→ 1 時間有効の ghs_…。App 未設定なら静的 GH_TOKEN にフォールバック
  3. VM の tmpfs に書く: ssh で /run/sandbox/env（umask 077）に TASK_ID / SANDBOX_PJ / SANDBOX_HOST / CLAUDE_CODE_OAUTH_TOKEN / GH_TOKEN / GH_REPO / GH_TOKEN_EXPIRES_AT
  4. login shell が読む: /etc/profile.d/sandbox.sh が /run/sandbox/env を export。/etc/profile.d/sandbox-app.sh が /etc/sandbox/app.env（テンプレート由来の非秘密設定）を export。sandbox ssh は常に bash -l で入るので両方が効く
  5. DNS と台帳: sb-gw の hosts に 10.77.1.NN task-<id> を足して reload。Mac の state.json に記録
Claude のトークンは claude setup-token の長期トークン（リフレッシュ回転が無いので複数 VM で同時に使っても衝突しない。ADR-0005）。GitHub のトークンは 1 時間で切れるので、Mac の launchd が 45 分ごとに gh-app refresh で貸出中 VM 全部を書き直す。差し替えは token set → reinject（巻き戻し無しで tmpfs だけ書き直す。起動中の claude プロセスは再起動が要る）。

5.3 release のとき: 何が消えて何が残るか

消える（rollback）

作業ブランチと未 push のコミット、DB の変更、/run/sandbox/env のトークン、起動中の claude、~/gates/*.log、/tmp、sudo で入れたパッケージ、bash 履歴

残る（テンプレート由来）

リポジトリ clone と依存、DB schema と seed、systemd ユニット、Mac の SSH 公開鍵、git の credential helper 登録、/etc/sandbox/app.env

外に残る

GitHub に push したブランチと PR、Mac の $AIFACTORY_WORKSPACE/runs/、Mac の state.json から削除された履歴（削除されるので残らない）、sb-gw の hosts から消えた task 行

5.4 ワークフロー 1 周（workflow/bin/spin-v0.sh）

sandbox の上に載る最小の AI developer workflow。動画の「build agent → コードで lint → 赤なら差し戻し」を bash で書いたもの。Mac 側で動き、VM の中には ssh で入る。

  1. sandbox take → gates.sh と依頼文（workflow/prompts/*.md）を VM に scp
  2. VM 内で git checkout -B sandbox/<id>-<slug> origin/develop
  3. VM 内で claude -p "$(cat prompt.md)" --dangerously-skip-permissions（隔離されているので権限確認をスキップ）
  4. 未コミットが残っていればコードがコミット → VM 内で bash ~/gates.sh（typecheck / test など。PASS / FAIL を 1 行ずつ）
  5. FAIL があれば、ゲート結果と赤ログの末尾を retry.md に書いて claude にもう一度（最大 MAX_LOOPS=2 回）
  6. git push → gh pr create --base develop（赤が残れば draft）
  7. 所見（ゲート結果、差分、PR URL、take までの秒数、全体秒数）を Mac の $AIFACTORY_WORKSPACE/runs/<date>-<pj>-<id>.md に書く → sandbox release
2026-09-06 02:53 に kumitate（task 101）と別 PJ（task 102）で「CLAUDE.md を実態に合わせて整理する」依頼で 1 周を開始した跡がある（$AIFACTORY_WORKSPACE/runs/）。この資料の作成時点では両 task が貸出中のままで、claude のログファイルは 0 バイト、run ファイルは依頼文までしか書かれていない。1 周が最後まで通ったかは未確認。STATUS.md の Step 6 も「未着手」のまま。

6.2 誰が何に届くか

主体届くもの届かないもの
VM 内のエージェント（dev、sudo NOPASSWD）自 VM の全部、同じ sbnet の他 VM（:22 は鍵が無いので入れないが :3000 や DB ポートは開いていれば届く）、sb-gw の DNS、Internet 全部（SNAT、制限なし）Proxmox ホストの API / ssh、Mac、tailnet の他の機器（sbnet から tailnet 側への経路は無い）
Mac の CLIProxmox root、sb-gw root、全 VM の dev
tailnet の他メンバーACL grant が autogroup:member なので、tailnet のメンバーなら 10.77.0.0/16 に届く。VM への ssh は鍵が要る。:3000 のアプリは認証なしで見える

6.3 割り切っている点（設計上の既知事項）

  • VM のホスト鍵検証は無効（StrictHostKeyChecking no）。巻き戻しとクローンで鍵が同じになるための割り切り。内部網限定
  • PostgreSQL はローカル trust、MySQL root は固定パスワード。VM の外からは届かない前提
  • エージェントは --dangerously-skip-permissions で動く。VM 隔離がその代わり。ただし外向きは無制限なので、リポジトリ内容や会話の外部送信を止める仕組みは無い（PJ のコードは受託先のもの）
  • 同一 PJ の 3 台は同じテンプレートから来ているので、テンプレートに残した何かは 3 台全部に等しく残る。焼く前の後片付けが唯一の防御
  • sb-gw の eth0 は LAN に足があり、tailscale の入口でもある。ここが落ちると Mac から届かない（代替は ④ の ProxyJump）

7. 動画が求める sandbox 像との対比（足りているか）

着想元は Dan Isler（IndieDevDan）の動画「FORGET Loop Engineering. Agentic Engineering is about THIS」（34 分、英語。出典は docs/source/README.md。動画と文字起こしはリポジトリに含めない）。動画は「sandbox の作り方」は一切語らず、ソフトウェアファクトリーの中で sandbox が果たすべき役割だけを述べている。だから問いは 2 段に分かれる。

  1. sandbox としての要件: 動画が sandbox に求めていることを、いまの Proxmox sandbox は満たしているか
  2. ファクトリーとしての要件: 動画のファクトリー像のうち、sandbox 以外（kanban / workflow / glue）がどこまであるか

7.1 動画が sandbox に求めていること（文字起こしから抜いた要件）

動画の記述（要旨）いまの sandbox判定
「worktree は始めるには良いが終着点ではない。エージェントごとに自分の計算機を与えると完全に隔離される」VM 1 台 = エージェント 1 体。DB・プロセス・ポート・ファイルすべて VM 内で閉じる。worktree の共有問題（DB・ポート）は原理的に無い満たす
「自分が sandbox に飛び込んで、作業・結果・Web ページ・テスト・アプリを見てレビューできる」sandbox ssh で中に入る、sandbox url でブラウザから :3000、cmux の surface が ssh になる。テスト結果は gates.sh の出力満たす
「複数の sandbox を並列に立てる。hotfix なら 3〜10 体を競争させて最速を採る」21 台常駐（PJ ごと 3 台）。同時貸出は CLI で自然にできる。ただし「競争させて最速を採り、残りを捨てる」オーケストレーションは無い（workflow 側の仕事）土台あり・制御は未
「ファクトリーが起動したらまず sandbox をセットアップし、その後にワークフローを選ぶ」（= sandbox の準備はコードが行う）take は 1 コマンドで、コードから呼べる契約になっている。spin-v0.sh が実際にコードから呼んでいる満たす
「作業が全部戻ってきたらマージして出荷」（成果物が sandbox の外に出る）ブランチ push と PR 作成は通る（別 PJ で確認済み）。スクショ・ログ・任意ファイルの回収は ssh cat 頼みで専用操作が無い。workflow/README.md の要求「lint / test の結果とスクショを外に出せる」は Step 6 で検証待ちコードは出る。他は手作業
「sandbox は使い捨てで、状態が次に漏れない」（明示はしないが、隔離の前提として繰り返し出る）RAM 込みスナップショット巻き戻し。DIRTY ファイルが消えることを確認済み。トークンは tmpfs で消える満たす（動画より厳密）
「sandbox 内で CI/CD を回し、失敗なら build agent に戻す」lint / typecheck / test は VM 内でコードとして回る（gates.sh）。CI/CD 本体（GitHub Actions）との接続は無し。台帳では既存の self-hosted runner に繋ぐ案のままローカルゲートのみ
「sandbox は今後世界の計算機の大半になる。デバイスは減り、sandbox は増える」（= 台数を増やせる設計）単一ノードで 99 台（VMID / IP の上限）。ノード跨ぎは未決（テンプレート複製か VXLAN）。電源は物理ボタン単一ノード内は伸びる
結論（sandbox としての要件）: 動画が sandbox に求めていること（隔離・人が入れる・並列・使い捨て・コードから作れる）は、いまの Proxmox sandbox で満たしている。動画は sandbox の中身を語っていないので、認証トークンの注入、専用網と DNS、RAM 込み巻き戻し、GitHub App による短期トークンといった部分はこのプロジェクトが自前で設計した「動画に無い上積み」になる。足りていないのは sandbox 単体の機能ではなく、sandbox から成果物（テスト結果・スクショ・ログ）を取り出す定型操作と、CI との接続の 2 点。

7.2 動画のファクトリー像と、4 区画の現在地

動画の要素担当区画現在地判定
Kanban / チケットが入口。「ただのコード、エージェント不在」。着地した瞬間にファクトリー起動kanban役割定義のみ。task-id は人が 3 桁で手入力未
ルーターがチケットを読み、chore / bug / feature / hotfix のどのワークフローかを決めるglue役割定義のみ未
scout agent → plan agent（探索と計画を分ける）workflow無し。spin-v0 は依頼文を人が書いて渡す未
build agent → コードの lint / format / typecheck / test → 赤なら build agent に戻す（ループ）workflowspin-v0.sh にある。ゲートはコード、赤なら結果を claude に戻す（最大 2 回）最小形あり
「同じセッション ID に差し戻す」（Agent SDK、コードとエージェントの分離）workflowspin-v0 は毎ループ claude -p を新規に起動する。前回の文脈は retry.md の文章でしか渡らない。Agent SDK は未使用分離はできている。継続は未
test agent（テスト一式をエージェントに任せる）workflow無し（テストはコードのみ）。動画も「まずはコードで」と言っているので現時点では妥当保留で妥当
エンジニアは冒頭（plan）と末尾（review）だけworkflowspin-v0 はその形（依頼文を書く → PR をレビュー）形はある
hotfix 専用エージェント + 人の承認 + 複数 sandbox で競争workflow + glue無し未
ワークフローごとにモデルを使い分ける（chore は軽量、plan は最上位）workflow無し（VM 内の claude 既定モデル）未
ステップ間の結果を置く場所（context engineering）glueMac の $AIFACTORY_WORKSPACE/runs/ に所見を書く程度。VM 内の ~/gates/*.log は release で消える最小形
「まず自分で end-to-end を通し、Mermaid に書き起こしてからコードにする」全体Step 6（手動 1 周）が未完了のまま spin-v0（コード化）が先行している。動画の順番と逆順序が逆
アプリ層ではなく agentic layer（プロンプト・スキル・ワークフロー）に投資する全体このリポジトリの方針そのもの（README、ADR）方針一致
結論（ファクトリーとしての要件）: 動画の像で「できている」のは sandbox と、その上の最小ループ（build → コードのゲート → 差し戻し）だけ。動画がファクトリーの核と呼ぶ入口（kanban）と振り分け（ルーター）、ステップ間の状態置き場は無い。これは設計どおり（「sandbox を最初に作る」という判断）で、sandbox が足りないのではなく、他 3 区画が未着手という状態。

7.3 動画に無いが、この sandbox が独自に決めたこと

  • 認証の扱い（Claude 長期トークンの tmpfs 注入、GitHub App の 1 時間トークン、PJ ごとのアカウント分離）。動画は認証に触れない
  • ネットワーク（専用網、subnet router 1 台だけ tailnet に入れる、split DNS）。動画は「自分の計算機」としか言わない
  • RAM 込みスナップショットで「起動済みアプリ」から始める。動画の sandbox は都度作る前提に読める
  • PJ ごとのテンプレート（複数 PJ 同居）。動画は単一プロダクト前提
  • 「gate（合否に使う）」と「info（記録だけ）」の区別。動画の「pass / fail」を、CI が守っていないテストが混ざる現実に合わせて 2 段にした

8.2 次の一手（この資料の対比から）
