1. 一言でいうと何か

「チケットを入れると、隔離された VM の中でエージェントが計画・実装し、コードがテストを回し、人間は最後にレビューだけする」工場です。着想は Dan Isler の動画で、要点は 3 つ。

アクター特性この工場での担当
コード速い・毎回同じ・トークン 0 円・最も信頼できる採番、配車、VM の貸出、ゲート（lint / test）、PR 作成、マージ、状態の記録
エージェント柔軟だが遅く高くブレる計画（planner）、実装（implementer）、調査（researcher）、レビュー（reviewer）
エンジニア（人間）最も高価冒頭の依頼と、末尾の PR レビュー・マージ判断だけ
設計原則は「コードとエージェントを分離する」。エージェントに lint を走らせるのではなく、コードが lint を走らせて結果をエージェントに戻す。だから workflow の step は agent step と code step の 2 種類しかありません。

2. 全体の流れ（1 枚の図）

上から下へ「何を → どう → どこで」。左から右へ時間。点線は結果の書き戻し。

言葉にすると: 自由文を intake が 1 枚のチケットにして kanban に起票する。dispatch が todo を取り出して runner を呼ぶ。runner は sandbox から VM を 1 台借り、workflow 定義どおりに step を順に回す。agent step は VM 内で claude -p、code step は gates.sh や pr-create.sh。最後に PR ができて人間に渡り、状態が kanban に戻る。

LLM はどこで動くか（workflow で動くのか？）

答えは「workflow では動かない。VM の中で動く」です。workflow（YAML）は「どの step で、どの役割が、どのクラスのモデルを呼ぶか」を書いた定義にすぎず、それを読む runner も Mac 上の Python です。runner は agent step に来ると、VM に ssh して claude -p "$(cat prompt.md)" --model <モデル> を起動し、終わるのを待ちます。LLM のプロセスは VM の中にあり、VM 内のリポジトリを読み書きします。

LLM ①LLM ②（参考）このセッション
誰が呼ぶglue/bin/intakeworkflow/bin/run（agent step）メンテナが対話している Claude Code
どこで動くMac（一時ディレクトリ、ツール無し）sandbox VM の中（$SANDBOX_APP_DIR が cwd、ツールあり）Mac
何回チケット 1 枚につき 1 回agent step ごとに 1 回。差し戻しがあればその回数だけ増える工場の外。工場を作る・直す側
モデルroutes.env の judgment（Fable）role の既定クラス → routes.env（planner / reviewer = Fable、researcher = Sonnet、implementer = Opus）Fable

出力JSON（pj / kind / title / body）→ kb newartifact（plan.md 等）と git コミットリポジトリの変更
LLM を呼ばないもの: kb（採番・状態）、dispatch（配車）、runner 本体（分岐と ssh）、gates.sh（テスト）、pr-create.sh / pr-merge.sh（GitHub 操作）、sandbox CLI（VM の貸出）。これらは Python か bash で、毎回同じ結果を返します。

3. 4 つの区画と実体

区画問い実体（ファイル）エージェントは居るか
kanban何をいつやるかkanban/bin/kb（CLI）、$AIFACTORY_WORKSPACE/kanban/kanban.db（状態の正本）、$AIFACTORY_WORKSPACE/kanban/tickets/<id>-<pj>-<slug>.md（本文の正本）、$AIFACTORY_WORKSPACE/kanban/BOARD.md（生成物）居ない（ただのコード）
glue区画をどう繋ぐかglue/bin/intake（自由文 → チケット）、glue/bin/dispatch（todo → 実行）、$AIFACTORY_WORKSPACE/logs/intake.log / dispatch.logintake が LLM を 1 回だけ呼ぶ。dispatch は居ない
workflowどう進めるかworkflow/kit/（定義: workflows / roles / steps / schema / routes.env）、workflow/bin/run（runner）、$AIFACTORY_WORKSPACE/runs/（実行記録）agent step で居る。step 間の分岐はコード
sandboxどこで動くかsandbox/bin/sandbox（Mac 側 CLI）、$AIFACTORY_WORKSPACE/projects/<pj>/（provision.sh / project.yml / gates.sh。無ければ examples/projects/<pj>/）、Proxmox 上の VM プールVM の中で agent が動く。貸出・巻き戻しはコード
PJ 固有のものは $AIFACTORY_WORKSPACE/projects/<pj>/ にしか無い。手順（workflow）は全 PJ 共通で workflow/kit/ に 1 つ。PJ を足すときは projects に 3 ファイルを置くだけで、workflow は複製しない（探索順は workspace → examples/projects/）。これが「手順を育てる場所を 1 つにする」という約束（ADR-0009）。

4. 1 枚のチケットの一生

kumitate の「カレンダーの週表示で月末の日付が欠ける」という依頼（kanban 207。説明用の例）を、bug workflow で回す場合に何がどの順で起こるか。

  1. intake 自由文を読む。先頭に pj: / kind: 行があればそれを採用（決定的）。無い分だけ Fable（judgment クラス）に 1 回聞き、PJ・種別・題名・本文（完了条件つき）の JSON を得る。kb new で起票。confidence とモデル名を本文末尾に残す
  2. kb new MAX(id)+1 で採番（207）。pj / kind が実在するか検証。$AIFACTORY_WORKSPACE/kanban/tickets/207-kumitate-….md を作り、DB に todo で記録。BOARD.md を再生成
  3. dispatch kb list --status todo を古い順に見る。その PJ に project.yml が無ければ blocked。プール（PJ あたり 3 台）が全部貸出中なら飛ばす。回せるなら kb run 207
  4. kb run 状態を in_progress にし、run ディレクトリ名（2026-09-06-kumitate-207。実体は $AIFACTORY_WORKSPACE/runs/ の下）を run 列に記録。workflow/bin/run kumitate 207 bug …/tickets/207-….md を呼ぶ
  5. runner 起動 kit/workflows/bug.yml と projects/kumitate/project.yml を読み、JSON Schema で検証。ブランチ名 sandbox/207-bug-<slug> を決める。state.json を作る
  6. take sandbox take kumitate 207。クリーンな VM を 1 台貸し出し、トークンを注入、DNS に task-207.sb.internal を登録（第 7 節）。runner は VM 内で git checkout -B sandbox/207-… origin/develop し、チケットを ~/work/207/ticket.md に置く
  7. plan（agent） runner が依頼文を組み立て（第 6 節）、VM 内で claude -p --model claude-fable-5-1。出力は ~/work/207/plan.md。無ければ step 失敗
  8. implement（agent） 依頼文に plan.md を含めて Opus 5。再現テストを先に書き、直し、コミット（push はしない）。report.md を書く
  9. gates（code） Mac 側の kit/steps/gates.sh が VM 内で projects/kumitate/gates.sh（tokens:check / typecheck / lint / test / test:dom）を実行。赤なら implement に戻す（最大 2 回、超えたら human）。known_red_gates にある赤は INFO 扱い
  10. review（agent） Fable が plan / report / gates の結果と git diff origin/develop...HEAD を読み、PASS / FAIL を review.md に書く。FAIL なら implement へ（最大 1 回）
  11. pr（code） kit/steps/pr-create.sh が push して PR を作る。宛先は project.yml の base_branch。次は human
  12. release ~/work/207/ を Mac の $AIFACTORY_WORKSPACE/runs/…/work/ に回収し、VM を clean スナップショットへ巻き戻す。VM に残るものは無い
  13. 状態の書き戻し kb が state.json を読む。PR あり → review、MERGED → done、PR 無しで end（research）→ done、human で PR 無し → blocked。BOARD.md 再生成
  14. 人間 PR をレビューしてマージ。マージ作業自体も merge-pr workflow で無人化できる（コンフリクト解消 → gates → review → merge）

5. workflow の中身（step と分岐）

workflow は YAML で、step の並びと結果に応じた行き先だけを書きます。step の担い手は role（agent）か code（スクリプト）のどちらか。

feature の流れ。青 = agent step、灰 = code step、赤矢印 = 差し戻し。
workflow流れ使いどころ
hotfixplan → implement → gates → review → pr本番障害の最小修正。宛先は hotfix_base
bugplan → implement（再現テスト先行）→ gates → review → pr不具合修正
featureresearch → design → implement → gates → review → pr機能追加
choreimplement → gates → prdocs・依存更新など判断の要らない雑務
researchresearch → judge → end調べるだけ。PR 無し。summary.md を回収
merge-prresolve → gates → review → merge既存 PR のコンフリクト解消とマージ。本文の pr: N 行で対象を指定

YAML の 1 step はこう書かれています（bug.yml の gates と review）。

  - id: gates
    code: gates.sh                 # code step。Mac 側 kit/steps/gates.sh が VM 内で PJ の gates.sh を実行
    outputs: [gates.txt]
    on_pass: review
    on_fail: { goto: implement, max_loops: 2, else: human }

  - id: review
    role: reviewer                 # agent step。kit/roles/reviewer.md の憲法で、judgment クラスのモデル
    inputs: [plan.md, report.md, gates.txt]
    outputs: [review.md]
    on_pass: pr
    on_fail: { goto: implement, max_loops: 1, else: human }

6. 設定はどこのものが使われるか

いちばん混乱しやすいところです。答えは「agent への依頼文は runner が 8 層を重ねて組み立てる」で、各層の出どころが違います。

組み立て結果は $AIFACTORY_WORKSPACE/runs/<run>/prompt-<step>-<n>.md に残るので、後から「agent は何を見ていたか」を読めます。

設定ファイル一覧

ファイル誰が読む何を決める変える頻度
workflow/kit/workflows/*.ymlrunner（起動時に schema 検証）step の並び、担い手、入出力、分岐と上限低。全 PJ に効く
workflow/kit/roles/*.mdrunner → agent（依頼文の 1〜2 層目）役割の憲法。やること・禁止・出力の形低
workflow/kit/routes.envrunner、intakeクラス → モデル（judgment = Fable / research = Sonnet / coding = Opus）低。メンテナの判断
workflow/kit/steps/*.shrunner（code step）gates.sh（PJ のゲートを VM で実行）、pr-create.sh、pr-merge.sh低
workflow/kit/schema/*.jsonrunnerworkflow.yml と project.yml の正しさ低
$AIFACTORY_WORKSPACE/projects/<pj>/project.ymlrunner、dispatch（有無だけ）、intake（PJ 一覧）PJ の事実と方針。repo / base_branch / app_dir / gates / facts / forbidden / review_points / known_red_gates中。PJ の状況で更新
$AIFACTORY_WORKSPACE/projects/<pj>/gates.shkit/steps/gates.sh（VM 内で）PJ の品質ゲート。CI と同じ組。PASS / FAIL を 1 行ずつ中
$AIFACTORY_WORKSPACE/projects/<pj>/provision.shProxmox 側 32-pj-template.shテンプレート VM の焼き込み（依存・DB・seed）低。テンプレ更新時
examples/projects/<pj>/上と同じ（workspace に同名の PJ が無いときだけ）同梱のサンプル PJ 定義（kumitate）。写して自分の PJ を作る雛形低
~/.config/sandbox/pj/<pj>.envsandbox CLI（take / reinject）PJ ごとの CLAUDE_CODE_OAUTH_TOKEN と GH_REPO。リポジトリ外トークン更新時
~/.config/sandbox/gh-app/sandbox CLIGitHub App の ID と秘密鍵。リポジトリ外ほぼ無し
~/.config/sandbox/state.jsonsandbox CLI、runner、dispatch、他セッションどの VM を誰に貸しているか。リポジトリ外take / release のたび
$AIFACTORY_WORKSPACE/kanban/kanban.db + tickets/kb、intake、dispatch、runner（本文）チケットの状態と本文高。日常運用
「PJ 固有のことを workflow yml に書きたくなったら間違い」。PJ 固有は project.yml の facts / forbidden / review_points に書く。逆に「全 PJ で毎回同じ注意」を project.yml に書くのも間違いで、roles/_common.md か roles/<role>.md に書く。

7. sandbox take の中で起きること

sandbox take <pj> <id> の 1 コマンドで、Mac 側 CLI が Proxmox とゲートウェイに ssh して次を行います。所要は約 10 秒（VM は起動済みで、RAM 込みスナップショットから戻るため）。

物理・ネットワークの詳細は sandbox-architecture.html。ここでは「take が何を用意するか」だけ。
  1. 貸出台帳 state.json から、その PJ のプールで空いている VM を 1 台選ぶ（無ければエラー）
  2. Proxmox で clean スナップショットに巻き戻す（前回の残骸を消す）。RAM 込みなので起動待ちが無い
  3. PJ の env（Claude トークン）と GitHub App の installation token（そのリポジトリ限定・1 時間）を /run/sandbox/env（tmpfs）に書く。runner は code step の前に払い出し直す
  4. sb-gw の dnsmasq に task-<id> を登録。Mac から sandbox ssh <id> と http://task-<id>.sb.internal:3000 が通る
  5. runner が VM 内で base ブランチを fetch し作業ブランチを切る。チケットを ~/work/<id>/ticket.md に置く

8. 秘密情報の流れ

秘密置き場（正本）VM への渡し方寿命
Claude Code の長期トークン（claude setup-token）Mac ~/.config/sandbox/pj/<pj>.env。PJ ごと（ADR-0006）take のたびに tmpfs へ注入。sandbox reinject で貸出中にも差し替え可巻き戻しで消える
GitHub の push / PR 権限GitHub App aifactory-sandbox の秘密鍵（Mac ~/.config/sandbox/gh-app/、ADR-0008）take のたびに、そのリポジトリだけに効く installation token を払い出して注入。権限は App が持つもの（contents / pull_requests write、metadata / actions read）1 時間。launchd が 45 分ごとに更新、runner も code step 前に更新
SSH 鍵（Mac → VM）Mac ~/.ssh/conf.d/aifactory/sb_ed25519テンプレートに公開鍵を焼き込みテンプレ更新まで
リポジトリには秘密を一切書きません。.gitignore が *.env / *.token を弾きます。VM 側は tmpfs なので、巻き戻し後に残りません。

11. 用語集

workflow
チケット種別ごとの手順。step の並びと分岐。kit/workflows/<name>.yml
step
1 回の呼び出し。担い手は role（agent）か code（スクリプト）
role
agent の人格と権限。憲法は kit/roles/<role>.md、モデルのクラスは routes.env
artifact
step の入出力。必ずファイル。VM の ~/work/<id>/ に置き、release で回収
transition
結果に応じた次の行き先。next / on_pass / on_fail。human は人間へ渡して終了
gates
PJ の品質ゲート（lint / typecheck / test / 静的解析）。コードが走らせ、赤なら agent に戻す
known_red_gates
base で既に赤いゲート。runner が FAIL を INFO に格下げし、範囲外の修正を防ぐ
take / release
VM の貸出と返却。返却は clean スナップショットへの巻き戻し
task-id
kanban が採番する 3 桁以上の番号。VM の名前 task-<id>、ブランチ、run ディレクトリに使う
run
runner の 1 回の実行。$AIFACTORY_WORKSPACE/runs/<date>-<pj>-<id>/。kanban の run 列にはこのディレクトリ名が入る
intake / dispatch
glue の 2 本。自由文 → チケット（LLM 1 回）、todo → 実行（ただのコード）
クラス（judgment / research / coding）
作業の種類。モデル名はクラス経由で解決する（判断は Fable、Web 調査は Sonnet、実装は Opus）
ADR
設計判断の記録。docs/adr/。1 判断 1 ファイル、書き換えず追記
