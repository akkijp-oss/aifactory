# ADR 0062: 起票は「方式を選ぶ → 入力する → 確かめて登録する」の 1 本道にし、1 画面 1 方式にする

- 状態: Accepted
- 日付: 2026-09-11

## 状況

起票画面（`#/intake`）は `console/static/app.js` の `viewIntake()` が `.grid2`（`1fr 1fr`）の中に
2 枚の `panel` を常時横並びで描いていた。左が自由文（`glue/bin/intake`。LLM が PJ・種別・題名・完了条件に整える）、
右が直接起票（`kb new`。書いたものをそのまま登録する）で、方式という状態を画面が持っていない。

そのため構造的に次が避けられなかった。2026-09-11 の実操作（Chrome、既定のデスクトップ幅）で確認した。

1. **PJ・種別・添付・助言・主操作が左右で重複する**。`class="primary"` の主操作が 2 つ並び、どちらを押すのかが構造で決まらない。
   `console/UX.md` の「操作領域の強いボタンは 1 つだけ」は、この画面にだけ適用されていなかった。
2. **「PR 番号（merge-pr のとき）」が種別と結線されていない**（`app.js` の `new-pr`）。既定の `bug` でも欄が出て、
   `actions['new']` はその値をそのまま送っていた。ラベルの括弧書きで補うしかなかった。
3. **「判定だけ見る」がチェックボックス 1 つ**（`in-dry`）だった。押しても何も起きないので、入れっぱなしに気づけない
   （「起票したつもりで起票できていない」が起きる）。さらに `actions['intake']` は dry-run でも `draftDrop(DRAFT_FREE)` していたので、
   `T.next.intakeDry` の「起票へ戻って取り込んでください」に従って戻ると、依頼文が消えていた。
4. **長文の行長が制御されていない**。各パネルが半幅になるだけで、読みやすい行長（measure）の指定は `.md` にしか無かった。

文言（2 方式の違い・登録と実行の分離・種別の用途・PJ の準備状態・本文の雛形）は `strings.js` に既にそろっている（#219 / #225 / #227）。
足りないのは構造と視覚の階層だった。

## 決定

1. **1 画面 1 方式**。段 1 で方式を選び、段 2 に選んだ方式のフォームだけを主領域に出し、段 3 で確かめて登録する。
   段の順は DOM の順そのままにする（`CSS order` で並べ替えない。ADR-0056）。
2. **方式の選択は素のラジオ**（`name="intake-mode"` の 2 つ）。`role="tab"` の ARIA パターンは使わない。
   roving tabindex の実装が要るうえ、この画面に前例が無い。素のラジオなら Tab・矢印キー・読み上げが何も足さずに効く。
3. **選んだ方式は下書きと一緒に持つ**（`sessionStorage` の `intake-draft.mode`）。ただし `DRAFT_FREE` / `DRAFT_NEW` には入れない。
   送信が通っても方式まで既定に戻さないため。切り替えの手は「今の欄を `draftSave()` → 方式を `draftPut()` → 描き直す」だけにするので、
   両方式の入力も選んだ PJ・種別・PR も残る。勝手に変換したり送ったりはしない。
4. **PR 番号は merge-pr のときだけ出す**。DOM からは消さず `hidden` を付け外しする（`draftSave()` の対象が生き、`hidden` なので
   Tab も読み上げも飛ばす）。`actions['new']` は種別が `merge-pr` のときだけ `pr` を送る（隠れている値を黙って送らない）。
   下書きの `newPr` は消さないので、merge-pr に戻せば値は戻る。
5. **dry-run はチェックボックスをやめてボタンにする**。段 3 を `primary`「取り込む」と通常ボタン「判定だけ見る」の 2 つにし、
   `dry_run` は押したボタンで決める。押した操作と結果が 1 対 1 になる。あわせて、**dry のときは下書きを捨てない**
   （`T.next.intakeDry` の案内が成立する）。
6. **添付は方式の切り替えでは残り、画面を離れると消える**。`picked` は落とす領域の id 別のメモリなので、
   `in-attach` / `new-attach` の id を据え置けば切り替えでは消えない。2 つの寿命を画面の言葉で分けて書く
   （`help.attachKeptOnSwitch` と `help.attachNotDraft`）。
7. **自分で書く方式は、送る前に Markdown の表示を確かめられる**。描画はチケット本文と同じ `md()` を使い、新しいパーサは増やさない。
8. **行長の上限は本文（`.md`）と同じ 78ch**。2 列をやめて空いた幅を、そのまま行長に流し込まない。
9. **起票から始まったジョブは起票へ戻るパンくずにする**。進行中・成功・失敗・できたチケットの出し分けは既存の `jobNext()` のまま使い、
   起票画面の中にインラインの状態表示は作らない（段階を分ける）。
10. **API と非同期ジョブは変えない**。`api('intake')` / `apiForm('intake')` / `api('tickets')` / `apiForm('tickets/{id}/attach')` の
    引数も `core.py` の返す形も据え置き、変えるのは呼ぶ画面の作りと戻り道だけ。新しい多段 AI 生成の基盤は作らない。

## 結果

- 主操作はどちらの方式でも 1 つになり、`UX.md` の原則が起票画面にも通る。
- 既定の `bug` で不要な PR 欄を要求しなくなり、merge-pr のときだけ「何に使うか」が欄の下に出る。
- 「判定だけ見る」を押したあと起票へ戻ると依頼文が残っているので、案内どおりにそのまま取り込める。
- 方式・両方式の下書き・選んだ設定は切り替えでも画面の往復でも残る。添付だけは画面を離れると選び直しになり、その旨を画面が言う。
- `strings.js` から `label.intakeDry`（チェックボックスの文言）と `label.prForMerge`（括弧書きのラベル）が消え、
  `btn.intakeDry` / `btn.preview` / `btn.previewClose` / `h.intakeStep1..3` / `help.modeFree` / `help.modeNew` /
  `help.modeKeep` / `help.prForMerge` / `help.preview` / `help.attachKeptOnSwitch` が入った。`sub.intake` の「左は / 右は」も書き換えた。
- これは**見た目と導線の改善という仮説**であり、初見の利用者の効率が上がることは未実証。1366 / 1024 / 390px と 200% 拡大、
  キーボードでの入力・切り替え・確認・登録は実ブラウザーで確かめた。
- 起票画面の中に非同期ジョブの状態をインラインで出すことと、共有ビューの統合は、この決定には含めない（次の票）。
