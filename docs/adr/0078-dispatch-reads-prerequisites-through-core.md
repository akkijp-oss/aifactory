# ADR 0078: 配車（dispatch）も先行条件を見る。判定は core の 1 か所を通し、飛ばした理由を残す

- 状態: Accepted
- 日付: 2026-09-15
- supersedes: ADR-0012 決定の「dispatch は…判断はしない」の 1 文（他の決定はそのまま）

## 状況

ADR-0077（#570）で票の先行条件を `depends_on` の 1 列にし、判定を `console/lib/core.py` に置いた。`kb next` は
「todo を id 順に 1 件返す」低レベルの口のまま変えていない（ADR-0074 決定 1）。これは設計としては正しいが、
**票を選ぶ経路が 2 つあることを見落としていた**。

| 経路 | 選び方 | ADR-0077 後の依存の扱い |
|---|---|---|
| `core.pm_status()` / `pm_decide()` | `kb next` → その後 core が判定 | 見る |
| `glue/bin/dispatch` | 自前の `next_ticket()` | **見ない（素通り）** |

つまり ADR-0077 が塞ごうとした事故（**止めてある票を機械が起動する**）が、`dispatch` という**もう一方の入口から
そのまま起きる**。ADR-0077 の「結果」節はこの穴を予告していた（「dispatch 側にも効かせるなら別票で core の判定を通す形にする」）。

実装を読んで分かった食い違いが 1 つある。#573 の票と ADR-0077 の本文は「`dispatch` は `kb next` を直接呼ぶ」と書いているが、
実際には `kb list --status todo` を id 順に舐めて `kb show <id>` を解析する自前の `next_ticket()`（`glue/bin/dispatch`）で選んでいる。
`kb list` も `kb next` も `ORDER BY id` なので選ぶ票は同じで、**どちらの経路でも依存を見ない**という結論は変わらない。

## 決定

1. `dispatch` は候補ごとに **`core.pm_unmet_deps(票)` を呼び**、未完了の先行票を持つ票を飛ばす。
   判定の規則（`depends_on` の読み方・`done` 以外は未完了・DB に無い id は未完了）を `dispatch` に書き写さない
   （ADR-0015「読み書きの正本は core」/ ADR-0074 決定 1 を継承）。`core` 側には `pm_unmet_deps` という公開名を 1 つ足し、
   `pm_status` もこれを通す。**規則が書かれている場所は 1 か所だけ**という状態をテストで機械的に守る。
2. 飛ばしたときは**理由を残す**。どの票を、どの先行票が（id と status）未完了だから飛ばしたかを、
   標準出力と `$AIFACTORY_WORKSPACE/logs/dispatch.log` の両方に出す。黙って対象外にしない。
3. `kb next` / `kb list` は変えない（ADR-0077 と同じ理由。低レベルの口に判断を入れない）。
4. `--resume-paused` の経路は対象外。`kb resumable` 由来で、**既に始まった run の続き**＝起動時の関門は通過済み。
   この経路の票は `depends_on` を持たないので `pm_unmet_deps` は空を返し、分岐は自然に効かない。必要になったら別票。
5. ADR-0012 の「dispatch は判断はしない」を「**種別（kind）の判断はしない。回せるかの機械的な確認
   （`project.yml`・プールの空き・一時停止・先行票）だけをする**」と読み替える。ADR-0012 の本文は書き換えない。

## 理由

- 同じ規則が 2 か所に書かれた瞬間、片方だけ直す事故が始まる。この repo が繰り返し踏んでいる型で、
  #573 そのものが「ADR-0077 で 1 か所直したら、もう一方が置き去りになった」という実例になっている。
  入口を増やさず、**判定の置き場を増やさない**方向で塞ぐ。
- `dispatch` から `core` は import できる（`console/bin/pm-tick` / `console/bin/mcp` と同じ 2 行）。`core` の依存は
  標準ライブラリと `lib/aifactory_*.py` だけで、import 時の副作用は置き場の解決だけ。
- 判定が足された分の「判断」は、既にある 4 つの飛ばし方（一時停止・回数超過・`project.yml` 無し・プール満杯）と
  同じ型＝「回せるかの機械的な確認」で、ADR-0012 が禁じた「種別や手順を dispatch が決める」ではない。

## 結果（トレードオフ）

- `dispatch` が `console/lib/core.py` に依存する。`core` が読めなければ `dispatch` は落ちる。
  これは握りつぶさない: **判定なしで素通しして止めてある票を起動するより、止まる方が安全側**。
- 同じ理由で、DB を引けないときも例外を上へ出す（`try` で「依存なし」に倒さない）。
  「先行票が無い」と「確かめられなかった」を混ぜない（`_pm_pick_next` と同じ方針）。
- 循環依存（a↔b）は検出しない。1 段しか見ないので無限ループはせず、両方飛ばして「todo が無い」で終わる。
  検出は必要になったら別票（ADR-0077 と同じ）。
- `dispatch` の 1 周で全 todo が先行票待ちだと、毎回 `kb show` を人数分叩いて「全部飛ばした」で終わる。
  件数が増えて遅くなったら、候補選びを `core` 側へ寄せる（`_pm_pick_next` 相当を 1 回呼ぶ）形に変えられる。
