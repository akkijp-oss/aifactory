# ADR 0055: 統計の日別は工程の時刻を「見る側の時間帯」に直した日付で切る（run 名の日付は変えない）

- 状態: Accepted
- 日付: 2026-09-10

## 状況

console の統計（`#/stats`）の日別（`by_day`）は、工程 1 行の日付を **run ディレクトリ名の先頭 10 文字**から取っていた（`console/lib/core.py` の `agent_step_rows` の `date`）。run 名の日付は `kb run` を起動した時点の制御系の `date.today()` で、制御系の時計は UTC で動いている。

そのため、日本で運転していると次の 3 つがずれる。

1. JST の 00:00〜08:59 に始めた run は、UTC ではまだ前日なので前日に数えられる。
2. 日付をまたいだ run は、後半の工程まで全部 run の開始日に載る。
3. 「直近 N 日」の起点（`stats_view` の `since`）も制御系の今日（UTC）から数える。JST の朝は「今日」が空になる。

一方、工程ごとの時刻 `at`（`ts_file` = 記録ファイルの更新時刻）はオフセット付き ISO 8601 で持っていて（ADR-0026）、画面の他の時刻表示は `fmtT` / `tzLabel` でブラウザーの時間帯に直している。日別だけが換算されていなかった。

## 決定

1. **日別と期間の基準は run 名ではなく工程の時刻 `at`。** `stats_view(days, pj, include_dry, tz=None)` が `tz` を受け、行ごとに `day = at をその時間帯に直した日付` を出して、`by_day` のキーと期間の絞り込みに使う。`since` も同じ時間帯の今日から数える。`at` が読めない古い記録だけ run 名の日付に落とす。
2. **時間帯は「見る側」が決める。** 画面はブラウザーの時間帯（`tzOffset()`）を `/api/stats?tz=` で渡す。MCP の `stats` も `tz` を受ける。省略したときはサーバー（制御系）の時間帯にする。`+09:00` のようなオフセットと IANA 名（`Asia/Tokyo`）の両方を受ける。
3. **読めない `tz` は 400 にせず、サーバーの時間帯に落として「実際に使った時間帯」を応答に返す。** 応答の `tz`（`{name, offset, label}`）を画面が日別の表に「日付は {tz} 基準で数えます。」として出す。
4. **run ディレクトリ名の日付は変えない。** 名前は他の画面・ログ・成果物の突き合わせに使う識別子なので、意味を変えない。代わりに、run 名の日付と集計日が違う行があることを画面の「読み方」に書く。
5. **集計の項目名は `date` のまま**にして、意味だけを「工程が載る日付」に変える。

## 理由

- **なぜ run 名を直さないのか。** run 名は `runs/<name>/` のディレクトリ名で、チケット・ジョブ・PR・ログの参照に使う識別子である。日付部分は名前の一部であって集計の軸ではない。名前を JST にすると、既存の記録と新しい記録で規則が変わり、突き合わせのほうが壊れる。統計の軸だけを直せば、壊れるものが無い。
- **なぜサーバーの時間帯に固定せず `tz` を受けるのか。** 制御系は UTC で動いていて、運転員は JST で読む。どちらか一方に固定すると、もう一方から見た「今日」が必ずずれる。他の時刻表示はすでに「見る側の時間帯に直す」（ADR-0026 とチケット 235）で揃っているので、日別も同じ約束に寄せるのが一貫する。
- **なぜ読めない `tz` を 400 にしないのか。** 統計は読むだけの画面で、`tz` は表示の都合の引数である。綴りを間違えた URL で画面が白くなる損のほうが、黙ってサーバーの時間帯に落ちる損より大きい。落ちたことが分かるように、実際に使った時間帯を応答に入れて画面に出す。
- **なぜ `at`（更新時刻）を使い、開始時刻を使わないのか。** 記録に工程の開始時刻が無い。`at` は記録ファイルの最終更新時刻なので、工程の終了時刻に近い値である。日付をまたいだ工程は終了日に載る。ここは記録の形を変える話なので、この変更では踏み込まず、「読み方」に一言書くだけにする。
- **なぜ項目名を `date` のままにするのか。** `by_day` の項目名を `day` に変えると、画面・MCP の利用側・ドキュメントの差分が広がるだけで、読む人に伝わる情報は増えない。意味の変化はこの ADR と画面の「読み方」で明示する。

## 結果（トレードオフ）

- 同じ記録でも、見る時間帯によって日別の行が変わる。日別の合計は時間帯をまたぐ境目で 1 日ずれて見える。基準は表の注記に出す。
- 期間の絞り込みが工程の時刻で効くようになったので、run 名の日付が古くても工程の時刻が新しい run（手で作った記録・作り直した記録）は「直近 N 日」に入る。テストの作り物もこの規則に合わせる必要がある。
- `at` は工程ごとに違うので、1 つの run が 2 日にまたがって載ることがある。上位の表（`top`）には run 名が並ぶので、run 名の日付と集計日が違う行が見える。
- 統計のキャッシュ（`jobs/stats-cache.json`）の形は変えていない。`at` はキャッシュした行の外側で毎回付け直すので、鍵（サイズと更新時刻）の互換は保つ。
- 時間帯の解決は `zoneinfo`（標準ライブラリ）に任せる。IANA のデータベースが無い環境では IANA 名が解決できず、サーバーの時間帯に落ちる。オフセット指定はデータベースに依存しないので、画面からの指定は常に効く。
