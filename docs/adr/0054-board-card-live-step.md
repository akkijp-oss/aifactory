# ADR 0054: ボードのカードは div + 題名リンク + 工程リンクの兄弟構成にし、突き合わせ用の稼働中 run（`runs_live`）には上限を掛けない

- 状態: Accepted
- 日付: 2026-09-07

## 状況

ボードには「動いている run」が 2 か所に出る。

- 上の帯（`in_progress` セルの `.live`）: run 中心の一覧。run 名・PJ・チケット番号・workflow・**今の工程と経過時間**・実行記録へのリンクを出す。並び順は run の開始順。
- 下の 5 列のカード: チケット中心の一覧。題名・種別・更新日時・メモだけ。並び順は台帳の並び。

板を見る人は題名で仕事を認識するのに、進み具合は帯にしか無い。同じ 1 件を番号で見比べる必要があり、並び順も違うので目で追う手間がかかる。

構造上の制約が 2 つあった。

1. **カード全体が 1 本のリンク**だった（`<a class="card" href="#/ticket/<id>">`）。中に実行記録への `<a>` を足すと `<a>` の入れ子になる。HTML として無効で、ブラウザーの解釈（外側を暗黙に閉じる）に挙動を委ねることになる。
2. **突き合わせに使えるデータが上限で切られていた**。`overview()` の `runs_active` は帯のために既定 6 件で切る（ADR は無いがチケット 248 で「上限を掛ける前に PJ で絞る」に直した）。カードは台帳の全チケットぶん引くので、7 本以上動いている PJ 未選択のボードでは 7 枚目以降のカードだけ工程が出ない、という「一部だけ欠ける」表示になる。

## 決定

1. **カードの外枠を `<div class="card">` にし、チケット詳細（題名）と実行記録（工程行）を兄弟の `<a>` にする。** カード全面のクリックは題名リンクの `::after`（`position: absolute; inset: 0`）で保ち、工程行だけを `position: relative; z-index: 1` でその上に出す。`<a>` の入れ子を作らずに「押した場所で行き先が変わる」を実現する。**工程行の読み上げ名（`aria-label`）は見えている文字（工程名と経過時間）で始め、その後ろに行き先を足す。** `aria-label` は中身を上書きするので、行き先だけを入れると主役の工程が読み上げから消え、見えている文字で指す音声操作も届かなくなる（`ticketLink` と同じ約束）。
2. **突き合わせ用に `overview()` へ `runs_live` を足し、上限を掛けない。** 中身は稼働中 run（`status == "running"`、PJ 絞り込み済み、`list_runs()` の新しい順）から `name / pj / task / workflow / next / started` と、`current` があるときだけ `step / since` を取り出した軽い形。帯が読む `runs_active`（上限つき）と `runs_active_n` は変えない。
3. **工程と経過時間はカードに寄せ、帯は件数中心にする。** 帯の実行中の行は `<PJ> <番号>`・workflow・開始からの経過だけにする。同じ数字を 2 か所で読ませない。
4. **`current` が無い run のカードには前の工程を出さず、`次は <工程>` を出す。** 状態判定（`run_summary` / `apply_liveness`）と工程の表示名（`stepName`）・経過時間（`since`）は既存のものをそのまま使い、新しい判定を作らない。`not_started`（記録なし）と `abandoned`（runner が居ない）はカードに何も出さず、これまでどおり帯の別枠で説明する。

## 理由

- **なぜ「行全体クリック」を捨てないのか。** `console/UX.md` は「行クリックで開く表は、開く先の名前を `<a>` にする（行全体のクリックだけに頼らない）」と決めている。題名を `<a>` にするのはその約束どおりだが、クリック領域まで題名の文字幅に縮めると 5 列すべてで当たり判定が狭くなる（退行）。`::after` の当たり判定は、DOM 上は 1 つのリンクのまま見かけの領域だけを広げるので、読み上げにも Tab 順にも余分なものが増えない。
- **なぜ突き合わせ用の一覧を別に足すのか。** 上限は帯（人が読む十数行）のためのもので、突き合わせ（機械が引く join）には別の要件がある。`runs_active` の上限を上げると帯が長くなり、上限を掛けたまま join すると一部のカードだけ工程が欠ける。用途ごとに形を分けるほうが、どちらの要件も曲げずに済む。上限を外しても実害が無いのは、稼働中 run の数が VM プールの台数（PJ × 3 台）で物理的に抑えられているから。
- **なぜ `runs_live` を全項目ではなく 6〜8 個の鍵に絞るのか。** カードが使うのは行き先（`name`）・突き合わせ（`pj` / `task`）・表示（`workflow` / `step` / `since` / `next` / `started`）だけ。`history` や `gates` まで載せると、5 秒ごとの再取得で稼働中 run の数だけ無駄が増える。
- **なぜ `step` を「`current` があるときだけ」入れるのか。** 開始前と工程の切れ目では `current` が無い。そこで直前の工程名を出すと「終わった工程を実行中」と読ませる。鍵の有無をそのまま「工程が言えるか」の判定にすれば、表示側に条件が 1 つで済む。
- **なぜ最新の attempt を選ぶ仕掛けを新しく作らないのか。** `list_runs()` は開始の新しい順に並ぶ。チケット番号で最初に一致したものを取れば最新の attempt になる（実行記録画面の `runOf` が同じことをしている）。`-attempt2` を名前から判別する必要はない。

## 結果（トレードオフ）

- 帯からは工程と経過時間が消える。台帳にチケットが無い run（削除されたチケット・記録から番号を補えない run）の工程は、どこにも出なくなる。その run は帯からリンクで実行記録に入って読む。
- カードのどこを押してもチケットが開く挙動は変わらないが、工程行の上だけは実行記録に行く。押し間違いは戻るで戻れる（可逆）。
- 題名リンクの `::after` は、同じカードの中で「title のツールチップでしか全文が読めない要素」を覆ってしまう。メモ（`.card .note`）だけは `position: relative; z-index: 1` で上に出す。代償はメモの 1 行ぶん（約 16px）がカード全面クリックから外れること。次に `.card` へ省略表示や `title` を足すときも、同じように上に出す必要がある。
- `.card` を使うのはボードの `viewBoard` の中だけなので、他画面への波及は無い。`<a class="card"` に戻すと入れ子が再発するので、テストがソース検査で弾く。
- `runs_live` は `overview` の応答を稼働中 run の数だけ大きくする。増え方が問題になるなら帯と同じ上限を掛け、カードの工程は「出せる分だけ」に落とす（帯の「ほか n 件」の案内は今までどおり）。
- JS を動かすテスト基盤が無いので、`::after` の当たり判定と Tab 順はソース検査（CSS と HTML の形）と目視で担保する。
