# ADR 0089: 票は「起票時の base sha」を持ち、run は VM で距離を測って依頼文の 1 行で古さを知る

- 状態: Accepted
- 日付: 2026-09-16

## 状況

チケット本文は**起票時点のコード**を `path:line` で引用する。base はその後も進む。両者の差は
機械が知っている（起票時の sha と現 tip があれば `git rev-list --count` で出る）のに、その差が run へ
一切伝わっていなかった。結果、run は**何十コミットも前の行番号を現在のものとして**渡されていた。

2026-09-14〜15 の kumitate で実際に踏んだ形:

| 票 | 起票時 base | 起動時の距離 | 実際のずれ |
|---|---|---|---|
| #526 | `df252fbf0` | 51 commits | `live-app-pane.tsx` :120→:127-128、`use-ai-chat-state.ts` :353-367→:420-434 |
| #527 | `df252fbf0` | 68 commits | 全引用が移動 |
| #521〜#524 | `df252fbf0` | 5〜40 commits | 毎回ずれた |

同じ板の #550 では、起票から数時間で `core.py:658` / `:1324` が `:663` / `:1428`（+5 / **+104**）にずれた。
同日の #535・#537 が `core.py` を +387 行伸ばしたためで、**半日で 100 行ずれる**。

これを埋めていたのは**管理役の手作業**だった。起動前に毎回 `git grep` で実測し、`kb append` で読み替え表を
貼る。効果は実測できていた（#522 以降の 3 run は GitHub API への無駄な呼び出しがゼロ）が、手作業である以上
管理役が代われば失われる。しかも 1 度は**手作業そのものが間違えた**——#527 の読み替え表を作る自作の検査が
path の quoting を誤り、実在する 4 ファイルを「不在」と報告した。貼っていれば run に「土台のファイルが
消えている」と伝えるところだった。

## 決定

1. **起票時の base sha は列で持ち、機械が刻む。** `tickets` に `base_sha TEXT` を足す。値は
   **対象 PJ の `base_branch` の tip commit**（aifactory 自身の sha ではない）。人間が本文に書くのではなく
   `kb new` が刻む——手で書く限り、抜けるか間違える。

2. **列の足し方は ADR-0077 が確立した形をそのまま使う。** `SCHEMA` の `CREATE TABLE`（新規 DB 用）と
   `ADDED_COLUMNS`（運用中の DB 用の冪等な `ALTER TABLE`）の 2 か所に足すだけで、新しいマイグレーション機構は
   作らない。同じ表に 2 通りの流儀を持たせない（ADR-0084 が踏襲したのと同じ理由）。

3. **刻むのは `kb new` の 1 か所。** 起票の口は利用者から見て 2 つ（`kb new` と `intake`）あるが、`intake` も
   console の `ticket_new` も `kb` を subprocess で呼ぶだけなので、実装は 1 か所で足りる（ADR-0015）。

4. **取得は `sync_pr` と同じ道で、失敗は全部「刻まない」に倒す。** `repo_for` → `gh_ready` →
   `gh api repos/<repo>/commits/<branch>`。repo / base_branch が無い・トークンを払い出せない・gh が居ない・
   10 秒で応答が無い・応答が sha に読めない、のどれでも `base_sha` は NULL のままで、stderr に理由を 1 行
   出すだけにする。**起票を落とすことは絶対にしない**（rc は変えない）。印は `[kb] warn:` で、console の
   `ticket_new` が `warnings[]` に拾う `[kb] warning:`（能力照合。#552）とは分ける。
   `--base-sha SHA` を `kb new` / `kb set` に置き、明示されたときは GitHub に聞かない（テストと手の訂正の口）。

5. **距離を測るのは VM の中。** 制御系は PJ の clone を持たない（git checkout をするのは runner だけ）ので、
   `kb run` は sha を `--base-sha=` で runner へ渡すだけにし、runner が base を fetch した直後に
   `git rev-list --count <sha>..origin/<base>` を 1 回だけ実行して `state.json` の `base_sha` / `base_distance`
   に残す。運び方は #594 が作った経路（`kb run` の CLI フラグ → `Run.refs`）と同じで、新しい運び方は発明しない。

6. **測れなかったときは 0 に丸めない。** 浅い fetch や force-push で sha を辿れないことがある。そのときは
   `base_distance` を `null` にし、依頼文にも「距離は測れなかった」と書く。0 に丸めると「ずれていない」と
   読めてしまい、**この ADR が塞ごうとした事故そのもの**になる。

7. **依頼文に出すのは 1 行だけ、位置は「## チケット」の直下・本文の前。** 引用の行番号を読み始める前に
   読ませたいので本文より前に置く（#594 の参照行は本文の後のまま動かさない）。依頼文は既に長い（#526 で 51KB）。
   **距離 0 の票と sha を持たない票では 1 行も足さない**——空行も増やさない。

8. **距離が大きいときの「引用所在の再測定」は researcher の役割文書に 1 行で書く。** 閾値は設けない。
   実データ（`state.json` の `base_distance`）が貯まってから決める話で、今は「注意行が在るなら測り直す」で足りる。

9. **行番号の自動追従はしない。** 票本文の自動書き換えもしない。機械で正しく解くのが難しい別問題で、
   本 ADR が引き受けるのは「**いつ時点のものかを伝える**」ところまでである。

## 結果

- 起票が GitHub App のトークン払い出しと `gh api` を 1 回ずつ挟むぶん遅くなる（+1〜3 秒・ネットワーク依存）。
  起票の口は intake（LLM 待ちの方が長い）と MCP なので許容と判断した。遅すぎると分かったら `--base-sha` の
  明示で回避できる。**自動取得を切る設定は作らない**（設定が増えると「刻まれていない票」の理由が増える）。
- 既存票（sha を持たない）は今までどおり動く。`TEXT` は NULL 許容なので、列を足しても既存行は NULL のまま
  ＝欠損時は警告を出さないだけになる。
- `base_sha` は `kb show` / `kb history` と、`SELECT *` で票を返す MCP / HTTP API からそのまま読める。
- dry-run と pull backend の run では VM で測れないので距離は `null` になり、依頼文は「測れなかった」の行になる。
- `start: pr` の workflow では `self.base` が PR の base に変わる。距離はそのときの base に対して測るので、
  票の sha と別ブランチなら数が大きく出うる。行が出るだけで害は無いので、特別扱いはしない。
- 名前が近い `base_sha256`（console の config 編集が使う版ハッシュ。ADR-0065 / ADR-0073）とは**無関係**。
  片方は git の commit sha、もう片方は編集の楽観ロックで、コード・テスト名でも書き分ける。
- 実 run での「古い票を起動して正しい commit 数が出る」は VM の中からは確かめられない（run の中から別の run は
  起こせない）。#552 / ADR-0084 で確立した分担どおり、実データでの確認は管理役が ctl 側で行う。
