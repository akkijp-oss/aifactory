# ADR 0072: モデルは「Agent + モデル名（表示名）」の 2 段で選ぶ。表示名と ID の固定の表を console に 1 つ持つ

- 状態: Accepted
- 日付: 2026-09-13
- 置き換え: [ADR-0065](0065-console-edits-model-settings-in-the-work-tree.md) の**決定 4 の最後の一文**
  「モデル名の固定の一覧は持たない（候補は今この設定で使われている値から作り、自由入力も受ける）」。
  決定 4 のそれ以外（書ける設定の範囲・値の形・鍵の系統の検査・鍵プールが空でも止めない）は、そのまま生きている。

## 状況

設定画面のモデルの欄は `<input list="...">` 1 つで、`claude-opus-5` のような**生のモデル ID を打つ**形だった。
候補（datalist）は `core.model_choices()` が「今この設定で使われている値」（`routes.env` の `MODEL_*` と全 workflow の実効 `model`）
から作るだけで、固定の一覧は無い。ADR-0065 の決定 4 がそう決めている。

運用して分かったこと。

- 運転員は ID を覚えるか、どこかから写してくる必要がある。`claude-haiku-4-5-20251001` のような日付つきの ID は特に写し間違える。
- **今この設定で使っていないモデルは候補に出ない。** 新しいモデルに替えるときは、最初の 1 箇所だけ必ず手打ちになる。
  「モデルを替える」は替えたいときにしかやらないので、候補が一番要る場面で一番効かない。
- どの Agent（実行する CLI）のモデルなのかが、ID の接頭辞にしか現れていない。今は claude しか無いが、コードにも画面にも軸が無い。

オーナーの指示（2026-09-13）で、決定 4 のこの一文を変える。

## 決定

1. **モデルの指定は「Agent → モデル名」の 2 段で選ぶ。** 1 段目は実行する CLI。**今は claude だけ**で、他は出さない。
   claude 以外を足せる器として形だけ 2 段にしておくもので、この決定では runner 側（`workflow/bin/spin-v0.sh`・鍵の系統・
   `token_family`）は何も変えない。2 段目は表示名（`Opus 5`）で、選ぶと ID（`claude-opus-5`）が決まる。
2. **表示名と ID の表（`console/lib/core.py` の `MODEL_CATALOG`）を正本にする。** 表は **1 か所だけ**に置く。
   画面（`app.js`）は API 越しに受け取って描くだけで、ID を写さない。文書にも ID を写さない（「表は core.py にある」と書く）。
   初期値は claude の 4 つ: Opus 5 / Sonnet 5 / Fable 5.1 / Haiku 4.5。
3. **この表は「画面で選べる既定の候補」であって、保存の許可一覧ではない。** 保存時の検査は ADR-0065 の決定 4 のまま、
   値の形と鍵の系統（`check_model_name`）だけを見る。表に無い ID でも、系統が分かれば保存できる。
4. **自由入力と動的な候補（`model_choices()`）は残す。** 2 段の選択は、従来の ID の入力欄に値を入れるための**見せ方の層**に過ぎない。
   ID の欄・その `datalist`・`POST /api/config/model` の入出力・`routes.env` と yml の書式は変えない。保存が読むのは今までどおり ID の欄 1 つ。
5. **表に無い値が設定に入っているときは、その ID をモデル名の選択肢に 1 行足して選んだ状態にする。** 画面が壊れず、値も候補も失われない。
   `routes.env` に無い `claude-fable-5-1`（plan 工程の `step.model` にだけある）のような「片方にしかない値」も同じ扱いになる。
6. **表を増やすときに直すのは `core.py` の表とこの ADR の理由だけ。** 画面・文書・検査に写さない（三重管理にしない）。

## 理由

- **なぜ固定の表を持つことにしたのか。** 「今使っている値から候補を作る」は、**替えたい先が候補に無い**という形で外れる。
  ID を覚えなくてよくするのが目的なら、まだ使っていないモデルこそ候補に要る。
- **なぜ自由入力を捨てないのか。** 表は必ず古くなる。新しいモデルが出た日に、表を直す PR が着地するまで画面から替えられない、
  では ADR-0065 が避けたかった状態に戻る。表は「速く正しく選ぶ道」、自由入力は「表が追いつかない日の道」で、役割が違う。
- **なぜ表を検査の許可一覧にしないのか。** 許可一覧にすると、表に無い ID が既に入っている設定（今の `claude-fable-5-1` が
  まさにそれ）を画面が拒むことになる。**選べること**と**保存できること**を分けておけば、表の更新漏れが事故にならない。
- **なぜ正本を `core.py` に置くのか。** 画面の JS に置くと、テストから表の中身を確かめるのに node が要る（node が無い環境では
  検査が飛ぶ）。core 側なら「表の全 ID が `check_model_name` を通る」を標準ライブラリだけで固定できる。
- **なぜ今 claude しか無いのに 2 段にするのか。** 後から段を増やすと、既に保存された値の読み替えが要る。今は入力の見せ方だけなので、
  器を先に作っても保存形式は 1 文字も変わらない。安いうちにやる。

## 結果（トレードオフ）

- 新しいモデルを表に出すには `MODEL_CATALOG` を直す PR が要る（着地までは自由入力で使える）。
- 表と実在するモデルのずれは機械では分からない。存在しない ID を表に残しても、選んで保存できてしまう（run が落ちて初めて分かる）。
  これは ADR-0065 が「鍵プールに無くても保存は止めない」と決めたのと同じ線で、「指定できる」と「使えるか未検証」を分けたまま。
- モデルの欄が 1 つから 3 つ（Agent の `select` / モデル名の `select` / ID の `input`）に増える。ID の欄は残すので、
  既存の操作（打って「変更を確かめる」）はそのまま通る。
- Agent の `select` は当面 1 択で、押しても何も起きない。将来の器であることは画面からは分からない。
