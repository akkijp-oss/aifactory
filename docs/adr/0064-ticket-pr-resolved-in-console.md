# ADR 0064: チケットの PR は console 側で「チケットの `pr` 列 + 実行記録の `pr_url`」から解決し、未登録を「存在しない」と言わない

- 状態: Accepted
- 日付: 2026-09-11

## 状況

チケット詳細から PR へ進む導線は、見出し脇の 1 か所しか無かった（`console/static/app.js` の `prLink()`）。
これは kanban DB の `tickets.pr` 列だけを見ていて、列が空なら何も描かない。

チケットの `pr` 列に番号が入るのは、`kanban/bin/kb` の `apply_result()` が run の `pr_url` から
`/pull/(\d+)` を抜いて転記したときだけで、それが走るのは **`kb run` の終了時と `kb sync` のときだけ**。
つまり実行中の run が PR を作っても、終わるまで（あるいは `kb sync` を叩くまで）チケットの `pr` 列は空のままで、
画面には何の導線も出ない。利用者からは「PR の欄が空」としか見えない。

一方、run の側には確認済みの PR が 3 通りの形で残っている。

- `human.pr_url` — 人間が wip から PR を作った後始末の記録（ADR-0039）
- `merged.pr_url` — runner が自分で条件を確かめてマージしたときの記録（ADR-0042）
- 生の `pr_url` — runner の `pr` ステップが書いた値

この 3 つは `run_summary()` が既に `ticket_detail()` の `runs[]` に入れて返している。
足りないのは「そこから 1 つ選び、チケット側の番号と突き合わせて由来を添える」ところだけだった。

また console は GitHub に問い合わせない（ADR-0050: PR の実在とマージ状態の正本は GitHub で、確かめるのは `kb sync` の
`gh pr view` だけ）。だから「番号が登録されていない」ことは言えても、「GitHub に PR が無い」とは言えない。

## 決定

1. **解決は console 側（`console/lib/core.py`）で導出し、記録には何も足さない。**
   `run_pr(r)`（run 要約 1 件 → 記録に残った PR 1 つ）と `ticket_pr(t, runs)`（チケット行 + `runs[]` → 解決結果）を足し、
   `ticket_detail()` の戻りにトップレベル `pr` を足す。`state.json` にも kanban DB にも新しい欄を作らない
   （ADR-0025 の「読み解きは console 側で導出する」、ADR-0039 の「`state.json` を書けるのは runner と `kb` だけ」）。

2. **フロントに置かない。** CI に JS を動かす基盤が無く、フロントの振る舞いはソース文字列検査でしか守れない（ADR-0058）。
   「複数 run」「不一致」「由来」の分岐は本物の単体テストで守りたいので Python 側に置く。
   `app.js` は `d.pr` をそのまま描くだけで、番号も URL も組み立て直さない。

3. **戻りは `{ticket, run, state}` の 3 つ組**で、`state` は `none` / `ticket` / `run` / `same` / `mismatch`。
   両方に番号があって食い違うとき（転記が古いまま残っている）は、どちらも消さずに 2 本並べて由来を添える。
   `runs` は `list_runs()` が `started` の降順に並べたものなので、先頭から見て最初に番号の取れた run を採る。
   採った run の名前は必ず戻りに入れ、画面がそれを出す（古い PR を現行と取り違えないため）。

4. **`run_outcome()` は触らない。** あちらも同じ 3 つを見るが、`reason` ごとに順を変える別の用途で既にテストがある。
   共通化のために既存の優先順位を動かす方が危ないので、優先順位が 2 か所に在るのを受け入れる。
   `run_pr()` の順は `human` → `merged` → 生の `pr_url` に固定し、それだけをテストで留める。

5. **未登録は「登録されていません」までしか言わない。** 「PR がありません」とは書かない。
   console は GitHub を見ていないので、無いと断定できる根拠を持っていない（ADR-0050）。

6. **読むだけの新しいパネルにし、編集欄には触らない。** 「項目を直す」の PR 番号欄（`set-pr`）とメモ欄はそのまま。
   外部リンクに `data-act` を付けない＝リンクを開いても内部の状態は変わらず、下書きの保護（ADR-0058 / ADR-0061）は
   今までどおり効く。表示が更新されても未保存のメモは消えない。

7. **DOM 順（ADR-0056）では「実行状況」の次・「本文」の前**に 1 枚置く。
   見出し → メモ → 実行状況 → **成果物** → 本文 → 添付 → 操作 → 実行記録 → ジョブ → 履歴。
   題名と今の状況の近くに成果物を出す、というチケットの求めに合い、本文を先に読ませる ADR-0056 の並びも崩さない。

8. **API のキー名は `pr`**。`ticket.pr`（番号だけの列）と紛らわしいが、`pr` は `state` を持つ別の形なので取り違えにくく、
   `ticket_detail()` の既存のトップレベルキーとも衝突しない。MCP の `ticket_show` にもそのまま乗る。

## 結果

- チケットに未転記でも、実行中の run が作った PR へチケット画面から 1 回のリンク操作で進める。
- `kb sync` を叩かせるために画面を往復する必要が無くなる。ただし転記そのものは今までどおり `kb` の仕事で、
  この表示は転記を代わりにやらない（DB は書き換えない）。
- 合成状態（未登録 / チケットだけ / run だけ / 一致 / 不一致 / 複数 run）は `console/tests/test_console.py` の
  `TicketPrTest` で守る。画面側は DOM 順とパネルのソース検査で守る。
- `repo` の無い PJ では URL を作れないので、番号だけを出して理由を 1 行添える。推し量った repo に番号を結び付けない。
- 5 秒ごとの再描画は `innerHTML` の差し替えなので、リンクに focus がある状態で更新が来ると focus が外れる。
  これは既存の全リンクに共通の挙動で、このパネルだけの問題ではないため、ここでは直さない。

## 代替案

- **フロントで `d.runs[0].human/merged/pr_url` を読む。** バックエンドを触らずに済むが、優先順位と不一致の判定が
  テストの無い場所に増える。MCP から同じことが読めない、という損もある。
- **`run_summary()` の `runs[]` に解決済みの値を足す。** run 一覧すべてに乗ってしまい、チケットとの突き合わせは
  結局どこかでやることになる。チケットの話はチケットの戻りに置く方が素直。
- **`kb sync` を自動で走らせて転記を先回りする。** 画面を開くたびに `gh` を叩くことになり、ADR-0050 の
  「確かめるのは `kb sync` のときだけ」を崩す。表示のために記録を書き換えるのも筋が悪い。
- **見出し脇の `prLink()` を拡張する。** 由来の 1 行も不一致の 2 本立ても、見出しの 1 行には収まらない。
  ボードのカードでも同じ関数を使っているので、そちらの 1 行も壊す。
