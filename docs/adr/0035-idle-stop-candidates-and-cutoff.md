# ADR 0035: idle-stop は 24 時間で候補にし、候補が 10 台を超えた分だけ古い順に止める

- 状態: Accepted（ADR-0033 の決定 1 を改める。他の決定はそのまま）
- 日付: 2026-09-09

## 状況

ADR-0033 の `sandbox idle-stop` は「貸出中でなく、最終利用から 3 時間経ったプール VM」を全部止めていた。これだと、日中に数回しか使わない PJ でも VM が毎回止まり、次の `take` のたびに起動と ssh 待ちの 30〜60 秒を払う。止める目的は CPU / メモリを空けることで、台数が少ないうちは空ける必要がない。

オーナーの指示（2026-09-09）: 最終利用から 24 時間経ったものだけを「消す対象」としてマークし、実際に止めるのは 10 台を足切りとして、それを超えた古いインスタンスだけにする。

## 決定

1. **判定を 2 段にする。** (a) 候補 = 貸出中でなく、最終利用から `N` 時間（既定 **24**。`SB_IDLE_STOP_HOURS` / `--hours`、`0` で無効、`pj/<pj>.env` で PJ 別に上書き可＝ADR-0033 のまま）経ったプール VM。(b) 止める = 候補を最終利用の古い順に並べ、新しい方から `K` 台（既定 **10**。`SB_IDLE_STOP_KEEP` / `--keep`、`0` で候補を全部止める）を残し、それより古いものだけ。候補が `K` 台以下なら 1 台も止めない。
2. **`K` は全体設定のみ。** 足切りはテナント全体の VM 台数を抑えるための数なので、PJ 別にはしない（PJ 別にすると合計が読めなくなる）。
3. **候補は `idle-stop.json` の `candidates[]`（`{vmid, name, last_used}`）に載せる。** `sandbox ls` / `status` の脚注に「N 台が停止候補」を足し、コンソールの sandbox 画面は起動中の候補に「停止候補」の印を付け、MCP `sandbox_status` も同じ JSON を返す。`stopped[]` の意味は変えない。
4. **止める直前にロックの中で判定し直す。** 候補集めはロック無しで全台を見て、止める `K` 台超ぶんだけ 1 台ずつ `state.json.lock` を取り、貸出・最終利用を読み直してから shutdown する（ADR-0033 決定 4 の「判定から shutdown 完了までロックを持つ」は維持）。候補集めのあとに `take` された VM は「判定のあとに状態が変わった」として見送る。

## 理由

- **なぜ 24 時間か。** 「今日使ったものは今日中は起きている」が運用の実感に合う。3 時間だと昼休みをまたぐだけで止まる。
- **なぜ足切りか。** 少数の VM が起きたままでも Proxmox は困らない。困るのはプールを増やしたときなので、台数で切る方が目的に直結する。
- **なぜ古い順か。** 残すのは「また使われそうな VM」で、最終利用が新しいほどその見込みが高い。
- **なぜ候補を記録するか。** 「止まっていないが、次に増えたら止まる」が見えないと、突然止まったように見える。脚注と印で先に知らせる。

## 結果（トレードオフ）

- プールが 10 台以下のテナントでは、既定のままだと VM は止まらない（旧来どおり常時起動）。止めたければ `SB_IDLE_STOP_KEEP` を下げる。
- 判定が 2 段になり、ログの要約行が `候補 C（停止 S / 残す K。足切り K 台）` の形に変わる。既存の `idle-stop.json` には `keep` / `candidates` が無いので、コンソールは無いものを `null` / `[]` として読む。
- `--keep 0` で ADR-0033 の動きに戻せる。
