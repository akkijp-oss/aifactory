# ADR 0087: 証明可能に死んでいる run でも `kb run-note` の門は開けない。記録上の後始末は退避で扱い、`finished` の有無という見方を 1 つに保つ

- 状態: Accepted
- 日付: 2026-09-16
- 関連: ADR-0039 決定 6（書き込みは終わった run にだけ）、ADR-0015（規則の正本を 1 つにする）、
  ADR-0053（`kb run --force` と二重再開のガード）、チケット 238（`.trash-runs` への退避・削除はしない）、
  チケット 236 / 584（`run_liveness` が残骸を `abandoned` と判定する）

## 状況

`kanban/bin/kb` の `human_note()` は、`state.json` に `finished` の無い run への `kb run-note` を断る。
ADR-0039 決定 6 のとおりで、**不具合ではなく意図して閉じた門**である。理由も同 ADR にある
（runner は実行中 `state.json` を書き直すので、同じファイルを 2 人が書くとどちらかの書き込みが消える）。

問題は、その目印が嘘をつく場合があることだった。**runner が異常終了すると `finished` が書かれないまま残る**
（take の失敗・SIGTERM・VM の再起動）。すると

- 守りたい「runner が今まさに書いている run」と、
- 閉じたい「runner が死んで `finished` を書けなかった残骸」

が、`finished` の有無だけでは区別できない。実際に、job が 1 秒で rc=1 終了し票は同日 done・PR も着地済みなのに
6 日間「実行中」と表示され続けた run（`<日付>-<pj>-<id>-attempt1` の形）と、`state.json` 自体が無い run が残った。
どちらも管理役が `kb run-note` で閉じようとして断られ、`$AIFACTORY_WORKSPACE/.trash-runs/` へ退避した（チケット 238 の作法）。

本 ADR は「**証明可能に死んでいる run を記録上終わらせる道を作るか**」を決める。

### 実測（本 ADR を書いた時点。参照は関数名で書く。行番号は古びる）

**1. 表示上の実害はもう無い。** チケット 584 の着地で `core.run_liveness()` が残骸を `abandoned` と判定するようになった。
判定材料は console が起動したジョブの終了記録と、台帳の票（`blocked` / `done` への更新時刻）で、
どちらも当たらなければ `running` のまま（根拠の無い run を勝手に中断にしない）。
＝ 画面が「待っていれば進む」と嘘をつく状態は解消済みで、残るのは run 記録そのものの見た目だけ。

**2. `kb` は `console/lib/` を import していない。** `kb` が通しているのは `lib/` の 4 モジュール
（`aifactory_paths` / `aifactory_attachments` / `aifactory_gh` / `aifactory_capabilities`）だけ。
逆向き（`core.py` が `kb` を subprocess で呼ぶ）は既にある。

**3. `run_liveness()` の材料は `kb` が持っていない。** 引数は `(s, jobs, tickets)` で、`jobs` は console の
JobStore が持つ起動記録。`kb` 側にはこれが無く、判定を `lib/` へ移しても「ジョブ記録を誰が渡すか」は残る。

**4. `"finished" not in s` は `kanban/bin/kb` に 5 か所ある**（`console/lib/core.py` には 0 か所。
`run_liveness` は `status == "running"` を見る別実装）。ただし**5 か所が同じ規則なのではない**:

| 関数 | 目的 | 分類 |
|---|---|---|
| `human_note` | `run-note` の書き込みを断る門（本 ADR の対象） | **規則の本体** |
| `run_in_progress` | 二重起動を止める。docstring が「`human_note()` と同じ見方。」と自己申告している | **同じ規則の複製** |
| `transcribe_human` | `human_note` を呼ぶ前の事前判定（呼べば同じ理由で断られる） | **同じ規則の複製** |
| `resume_plan` | 終わった run の再開材料を読むだけ。書かない | 別目的で同じ式 |
| `apply_result` | `finished` 無し + rc≠0 → 票を `blocked` にする（チケット 238） | 別目的で同じ式 |
| `core.run_liveness` | 表示上の残骸判定 | 別実装（ジョブと票も見る） |

→ **「runner が生きている＝書いてはいけない」という同じ規則は 3 か所**（`human_note` / `run_in_progress` /
`transcribe_human`）。同じ式を別目的で使うのが 2 か所、別実装が 1 か所。

**5. 公開契約は 2 系統ある。** ADR-0039 決定 6（設計記録）と、`website/content/ja/reference/cli-kb.md` の
`kb run-note` の節（en 側にも対応する記述）＝**利用者向けの約束**。同じファイルには `finished` 無しのときの
状態対応表もあり、`kb run --from` の節（ADR-0053）も `finished` の有無を根拠に書かれている。

**6. 門の退行テストは既にある。** `workflow/tests/test_kb_run_note.py` の
`test_a_running_run_is_not_written`。

## 決定

1. **案 A を採る。`kb run-note` の門は `finished` の有無のまま**とし、`run_liveness` の `abandoned` 判定には
   紐づけない。「証明可能に死んでいる run を記録上終わらせる道」は**作らない**。
2. **ADR-0039 決定 6 は読み替えない。** 例外も但し書きも足さない。断る条件は今までどおり
   「`finished` が無い」「既に `human` がある（`--force` なし）」の 2 つだけ。
3. **残骸の後始末は退避のまま。** `$AIFACTORY_WORKSPACE/.trash-runs/` へ人が動かす（チケット 238 の作法・
   削除はしない）。`.trash-runs` への退避を機械にやらせることは本 ADR の範囲外で、決めていない。
4. **`--force` を 3 つ目の意味で再利用しない。** 既に `kb run-note --force`（人間の記録の上書き）と
   `kb run --force`（実行中の票でも `--from` 再開を通す・ADR-0053）で意味が違う。
   将来この門を開けるとしても、名前で許すのではなく判定で許すこと。
5. **`"finished" not in s` の複製は現状維持**とし、次に触る人への注記だけを残す:
   **同じ規則は `human_note` / `run_in_progress` / `transcribe_human` の 3 か所。直すなら 3 つ同時に。**
   `resume_plan` / `apply_result` の 2 か所と `core.run_liveness` は**目的が違うので混ぜない**
   （ADR-0015 の「規則の正本は 1 つ」に照らせば直す価値のある複製だが、本 ADR はそこを範囲に含めない）。

製品コードの差分はゼロ。本 ADR と `docs/adr/README.md` の一覧行だけが変更である。

## 理由

- **門は目的を果たしていて、開けると事故の余地が戻る。** 守っているのは「runner が生きているのに人が同じ
  ファイルを書く」ことで、これが起きると書き込みのどちらかが黙って消える。得られるのは記録の見た目だけ。
- **実害はもう消えている。** 表示が「実行中」と言い続ける問題は 584 で直った（実測 1）。
  票の側も `apply_result` が rc≠0 の run を `blocked` にするので、**死んだ runner の票は既に守られている**。
  残っているのは run 記録の欄が埋まらないことだけで、P3 に見合う損失ではない。
- **公開契約が 2 系統ある**（実測 5）。開けるなら ADR 1 枚では足りず、ja / en の website も書き換わる。
  ADR は内部の決定だが website は利用者との約束で、重みが違う。
- **頻度が低く、逃げ道が既にある。** 起票時の実測で 411 run 中 3 件（0.7%）。退避という運用の手当てもある。

### 採らなかった案

**案 B: `run_liveness` が `abandoned` と判定した run に限って追記を許す。**
考え方としては正しい（名前ではなく判定で許す・ガードの前提が偽であることを機械で示す）。採らなかったのは:

- **依存が双方向になる。** `kb` は `console/lib/` を import していないのに、`core.py` は `kb` を subprocess で
  呼んでいる（実測 2）。`kb` → `core` を足すと相互依存になる。
- **判定を `lib/` へ移しても解けない。** `run_liveness` はジョブの起動記録と台帳を材料に取り、`kb` はそれを
  持っていない（実測 3）。移すと引数の出どころも一緒に動く。
- **規則の複製が増える方向に働く。** 同じ規則が既に 3 か所にある状態で（実測 4）、門だけ別の判定に切り替えると
  `run_in_progress` / `transcribe_human` と食い違う。二重起動は止めるのに書き込みは通る、という不整合が生まれる。
- **書き換えが ADR に閉じない。** ja / en の `reference/cli-kb.md` 2 系統と、退行テストの追加が要る（実測 5・6）。

**案 C: runner が異常終了しても `finished` 相当を残せるようにする**（ジョブの終了記録から導く・`state.json` に
runner の識別子を持たせて死活を見る）。根本に近いのは確かだが **runner 側の変更**で、案 B より範囲が大きい。
本票は P3 で、しかも守るべき実害（票の状態・画面の表示）は既に手当て済み。費用が釣り合わない。

## 結果（トレードオフ）

- 受け入れるもの: runner が異常終了した run の記録には、人間の後始末（`human`）が入らないままになる。
  console の画面では `abandoned` と出るので誤解はされないが、**「誰がどう始末したか」は run 記録には残らない**。
  残したい場合は票の側（`kb note`）に書く。
- 得るもの: 「`finished` が無い＝書いてはいけない」という見方が 1 つのまま保たれる。門・二重起動・転記の 3 か所が
  同じ答えを返し続ける。公開文書（ADR-0039 と website）も現行のままで正しい。
- この判断を覆す条件: 残骸の割合が目に見えて増える（例えば 1 割）か、`.trash-runs` への退避が運用として
  回らなくなったとき。そのときは案 B ではなく**案 C（目印そのものを正す）**から検討する。目印が嘘をつくことが
  問題なのであって、嘘をついた目印を迂回する道を増やすことではないため。

## 未確認

- **残骸の件数を数え直せていない。** 票にある「411 run 中 3 件（0.7%）」は起票時（2026-09-15）の値。
  本 ADR を書いた環境には運用データ（`$AIFACTORY_WORKSPACE`）が無く、`run_liveness` が `abandoned` を返す
  run を数えられない。決定は「頻度が低い」ことだけを根拠にしてはいないので、値が多少動いても成り立つ。
- **退避済みの実データ（`.trash-runs` の 2 件）を読んでいない。** 同じ理由で、この環境からは見えない。
  案 B で実際に閉じられる形だったかは確かめていない。退避したものは戻さない（記録の改変になる）。

## 状態

Accepted。ADR-0039 決定 6 を**そのまま維持する**ことを明文化し、チケット 584 が bug 票の中で意図的に
触らなかった門の扱いに答える。既存 ADR は書き換えない。
