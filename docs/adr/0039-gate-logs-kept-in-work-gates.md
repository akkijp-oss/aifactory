# ADR 0039: 赤いゲートのログは `work/gates/<名前>.log` に残し、実装役へ戻す依頼文の抜粋はそこから作る

- 状態: Accepted
- 日付: 2026-09-07

## 状況

PJ の `gates.sh`（例 `examples/projects/kumitate/gates.sh`）は、ゲート 1 つの全出力を VM の `~/gates/<名前>.log` に書き、標準出力には `PASS <名前>` / `FAIL <名前>` の判定行だけを出す。runner が回収するのは `work/gates.txt`（判定行と、#330 で足した赤いゲートの末尾 60 行）で、**どのテストがどのエラーで落ちたかの全体は VM の中にしか無い**。

- VM は run の終わりに `release` でテンプレートへ戻る。**終わった run の赤はもう誰も読めない**。
- 読みたい人は `state.json` の貸出先 IP を見て ctl 経由で VM へ ssh し `grep` する運用になっていた（2026-09-09 だけで 5 回）。run が終わっていればそれもできない。
- 実装役へ戻す依頼文（retry_note）に入るのは `kit/steps/gates.sh` の標準出力（判定行と `=== base check:` の結果）だけで、HEAD 側のログは入っていない。実装役は VM の中で自分で `~/gates/<名前>.log` を探すところから始める。reviewer と PM には最初から届かない。

## 決定

1. **HEAD で赤かったゲートのログは `kit/steps/gates.sh` が `$WORK/gates/<名前>.log` に残す。** runner の回収は `release()` の `scp -r`（再帰）なので、`$WORK` の下に書けば `runs/<run>/work/gates/<名前>.log` として自動で回収される。runner の回収処理は変えない。
2. **残すのは全文ではなく「エラーらしい行の抜粋 + 末尾 N 行（既定 300）」**。抜粋は `✗|×|FAIL|Error|error:|Traceback` に当たる行の先頭 100 件。ヘッダ 1 行に元のバイト数・行数・どこから取ったかを書く。
3. **1 ゲート 200KB を上限にし、超えたら末尾を優先して切る。** 失敗にはせず、`[truncated: kept last <n> bytes of ~/gates/<名前>.log]` の 1 行を先頭に残す（ADR-0034 と同じ扱い）。行数・バイト数は env（`GATES_LOG_LINES` / `GATES_LOG_MAX_BYTES`）で上書きできる。`project.yml` の項目は増やさない。
4. **INFO に落ちたゲート（`known_red_gates` と「base でも赤」）もファイルは残すが、実装役へ戻す依頼文には入れない。** 「元から赤い」の根拠を reviewer と人が run の記録だけで確かめられるようにするため。直す相手は実装役ではないので依頼文には載せない。
5. **依頼文の抜粋は runner が `work/gates/<名前>.log` を読んで組み立てる**（`gates.sh` の標準出力には足さない）。載せるのは `gates.txt` の判定行に残った `FAIL` だけで、1 ゲートあたり抜粋部の先頭 40 行・末尾側 40 行・3000 字まで。
6. **`$WORK/gates/` は gates step のたびに作り直す。**
7. **console と MCP は変えない。** `run_show` は run ディレクトリを `rglob` で再帰的に列挙し、`read_file` は `runs/` 配下なら読めるので、`work/gates/*.log` は無改修で一覧に載り読める。分類は「その他」のまま。

## 理由

- **なぜ `$WORK` に書くのか。** 「ログを回収する仕組み」を新しく作るより、既にある回収経路（`scp -r`）に乗せるほうが壊れる場所が少ない。gates.sh が書くだけで、runner・console・MCP のどれも変えずに「run 終了後も読める」が成立する。
- **なぜ全文ではないのか。** VM → runner の転送量と、依頼文に入る量。ゲートの全出力はビルドログを含むと数十 MB になる。読みたいのは失敗の理由で、それは普通は末尾か、エラー行の周辺にある。
- **なぜ標準出力ではなく別ファイルから抜粋するのか。** 標準出力は `run_code` が `out[-4000:]` に切って依頼文へ渡す（ADR-0038 の契約: 標準出力 = 判定行 + base 確認の結果）。ここにログを足すと、末尾 4000 字に押し出されて **判定行と `BASE-CHECK-SKIP` が消える**。判定は依頼文の文言（「base で確かめ済み」か否か）を決めているので、消えると実装役に嘘を伝えることになる。
- **なぜ INFO の分もファイルは残すのか。** 「base でも赤い」を機械が判定した根拠（#330）は今は `gates.txt` の末尾 30 行だけ。run が終わった後に人がその判定を疑ったとき、HEAD 側のログが無いと確かめようがない。
- **なぜ console の見せ方を変えないのか。** ゲート名は PJ ごとに違うので `workflow.yml` の `outputs:` には列挙できず、成果物として意味づけするには `run_groups` の作りを変えることになる。run 画面は別チケット（#335）が触っている。ファイル一覧に載って読めれば目的（終わった run の赤を読む）は足りる。

## 結果（トレードオフ）

- run ディレクトリが赤いゲートの数 × 最大 200KB だけ大きくなる。全緑の run では 1 バイトも増えない（赤が無ければログを取りに行かない）。
- 抜粋の正規表現は PJ のテストランナーの語彙に依る。当たらなくても失敗にはせず、抜粋節が空で末尾 N 行だけが残る。
- ゲート 1 つにつき ssh が 1 往復増える（赤いゲートの分だけ）。
- ログは `work/gates/` に「その他」のファイルとして並ぶ。どのゲートかはファイル名で読む。意味づけ（成果物としての表示）が要るなら別票にする。
