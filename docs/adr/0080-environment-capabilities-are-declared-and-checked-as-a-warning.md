# ADR 0080: 実行環境の「できないこと」は PJ 定義が宣言し、完了条件との照合は**警告だけ**にする。判定は 1 か所、未宣言は照合しない

- 状態: Accepted
- 日付: 2026-09-15

## 状況

実行環境の能力が暗黙知だった。結果として **実行環境に存在しない手段を要求する完了条件**がそのまま受理され、
run はそれを満たせないまま PR を出す。人（エージェント）は正しく振る舞っているのに、機械が最初から
無理な約束を受理しているのが構造だった。

- kumitate #526 / PR#400: 完了条件の「ローカルの認証付き合成データと**ブラウザ**で実 iframe を検証」が
  実施できないまま着地した。実装役も reviewer も「未実施」と明記して渡し、管理役もそれを台帳へ残してマージした。
  ★**ゲート 8 本が緑であることは、この条件を満たした証拠ではない**。機械はこの区別をしていなかった。
- kumitate #528 / #529: `make e2e` のフル実走と「意図的にエラーを起こして画面を読む」検証は docker スタック +
  実ブラウザが要る。管理役が両票へ「sandbox では実行不能」と注記して**起票段階で手で止めた**。
  本来機械が持つべき判定を人間が代行していた。
- 外部からバイナリを取得できない環境で、**取得失敗をエラーとして報告せず**「取得手順を README に書いて完了扱い」に
  した事例が 2 回連続で起きている。

一方で、能力の有無に応じて依頼文を変える経路は既にあった（`computer_use: true` のとき `build_prompt()` が
「## VMの画面操作」節を足す）。足りなかったのは「**無い**こと」を書く語彙と、それを完了条件と突き合わせる場所である。

## 決定

1. **能力は PJ 定義（`project.yml` の `capabilities`）が宣言する。backend から機械的に導かない。**
   キーは `browser` / `docker` / `egress` / `gui` の 4 つ固定（`additionalProperties: false`、全キー任意）。
   同じ backend（proxmox）でも焼いたテンプレートによって道具は違う——この VM の実測（2026-09-15）でも
   docker と podman は無く、`DISPLAY` も無いが、`google-chrome` はヘッドレスで在り、HTTPS の外向き通信は通った。
   「backend ごとの能力表」は機械的には決まらないので、**その PJ が使うテンプレートを知っている PJ 定義**が正しい置き場である。

2. **書いていないキーは「未宣言＝照合しない」。`false`（無いと確かめた）とは別に扱う。**
   ADR-0077 決定 4 と同じ型の区別で、「読めていない」を「確かめた結論」と混ぜない。
   実測できていない能力（例: kumitate の `egress`）は **書かない**のが正しく、`false` と書いて安全側に倒すのではない。
   `computer_use: true` は gui ができるという実質の宣言なので、`capabilities.gui` が無いときだけそこから導く
   （他の 3 つは導出しない）。schema の `allOf` に「`computer_use: true` なら `capabilities.gui` は `false` にできない」を 1 条足す。

3. **照合は警告だけで、起票も起動も止めない。** 完了条件は自由文なので、誤検知（例示として触れただけ）と
   取りこぼし（言い回しが辞書に無い）が**必ず**出る。ADR-0077 はこの性質を理由に依存関係の自由文解釈を**やめた**が、
   ★やめられたのは依存が `depends_on` という 1 列に構造化できたからである。完了条件は構造化できない。
   そこで**同じ前提から違う結論**を採る: 自由文は読むが、その結果を**決定に使わない**。
   `kb new` / `intake` / `ticket_new` は rc も戻り値の形も変えず、警告を添えるだけ。
   PM の選択にも工程の遷移にも影響させない（配車・遷移の判断材料にしない）。

4. **判定の正本は `lib/aifactory_capabilities.py` の 1 か所。語彙もそこに固定辞書として置く。**
   PJ ごとに語彙を持たせない（PJ 定義に書けるのは「能力の有無」だけで、「何を実行不能と見なすか」ではない）。
   入口（`kb` / `intake` / `core` / `run`）は lib を呼ぶか、lib を呼んだ側の出力を拾うだけにする（ADR-0015 の継承）。
   照合の対象は本文の `## 完了条件` 節のみ。節が無い本文は全体を見て、その旨（`scope: body`）を警告に添える。

5. **LLM に能力を教えない。照合は LLM の後の決定的なコードで行う。**
   `intake` の整形プロンプトに「この環境にはブラウザが無い」と書くと、LLM は完了条件を**弱める**方向へ倒れる。
   目的は実行できないことを可視化して人へ渡すことで、条件を緩めることではない。
   ADR-0012 の「判定は LLM 1 回、以降はコードの経路」とも揃う。

6. **`report.md` の `## 未検証項目` を必須にする。空欄の報告は受け取らない。**
   依頼文に「この環境で検証できないこと」を入れるだけでは、#526 と同じく実装役の良心頼みのままになる。
   runner は role が implementer の step の後に `report_unverified()` で節を読み、節が無い・中身が空なら
   「出力が無い」と同じ扱い（人間へ）にする。**「無し」と書けば通る**——書くことを増やす仕掛けではなく、
   空欄のまま出せなくするだけである。reviewer は未検証項目と依頼文の照合結果が整合するかを見る。

7. **★実行できないから完了条件を削る、という方向へは倒さない。** 依頼文にも役割の説明にも「条件を削らない・
   弱めない」と明記する。完了条件の自動書き換えは範囲外である。

## 理由

「ゲートが全部緑」は「完了条件を満たした」ではない。この 2 つを機械が区別していなかったことが #526 の構造であり、
区別を持ち込む最小の道具が「環境の宣言」と「その宣言に反する要求の可視化」である。

ブロックではなく警告にしたのは、★**止めると誤検知のたびに起票が滞り、運用は照合を切る**方向へ進むからである。
警告は外れても誰も止めない。辞書を育てる材料（`kb capcheck`）を先に用意し、実データで測ってから語彙を足す。

## 影響

- `project.yml` に `capabilities` が増える（任意。書かない PJ の挙動は一切変わらない——警告も出ず、依頼文の節も出ない）。
- `kb new` / `intake` の rc と標準出力は変わらない（警告は stderr）。`ticket_new` の戻りに `warnings[]` が増える。
- `project_show` に `capabilities` が増える。
- 宣言を持つ PJ の依頼文に「## この環境で検証できないこと」が 1 節増える（全役割）。
- 実装役の `report.md` に節が 1 つ増える。空欄で出すと人間へ戻るので、`implement` が人間待ちになる回数は増えうる。
  多発するようなら `on_fail` を足す判断を別票で行う。
- `kb capcheck` が増える（DB を変えない読み取り専用の測定口）。誤検知率は実運用の板を持つ環境で測る。

## 代案

- **backend ごとに能力表を持つ**: 同じ backend でもテンプレートで道具が違う（上の実測）ため、嘘の表になる。
- **ブロックする**: 誤検知が起票を止め、運用が照合ごと切る。ADR-0077 が自由文解釈を捨てた理由をここでも繰り返すだけになる。
- **完了条件を機械が書き換える**: 目的（人へ渡す）と逆で、★チケット自身が範囲外と定めている。
- **語彙を `project.yml` に持たせる**: PJ ごとに辞書がずれ、どの票がなぜ警告されたのか説明できなくなる。
