# ADR-0019: コンソールの操作は危険性に比例した摩擦で守り、文言は 1 か所に集めて検査する

日付: 2026-09-07 / 状態: 採用 / 決定者: メンテナ（「このノウハウを元にして console の UI/UX を改善してほしい。コストよりも品質を求める」）

## 状況
- Web コンソール（ADR-0013 / 0015 / 0017）は v0 のまま実運用に入り、貸出先（テナント）の運転員にも渡す段になった。画面は動くが、次の癖が残っていた
  - 本番 run・配車・返却・停止のすべてをブラウザ標準の `confirm()` で同じ見え方にしていた。可逆な状態変更にも危険な返却にも同じ摩擦で、確認を読まずに押す癖がつく
  - 操作の「後」が設計されていなかった。intake のジョブが終わっても、できたチケットへの導線が無い。run が途中で止まっても次の一手が文で書いてあるだけ
  - 文言が `app.js` のテンプレートに直書きで、「まだ無い」「要る」の言い切りと「〜します」が混在し、`rc` / `pid` / `task` のような開発者の語彙が列名に出ていた
  - 配車は「取り込み」画面の奥にあり、毎日使う操作なのにボードから 1 クリックで届かなかった（1 件配車のボタンだけがボードに居た）
- メンテナから SaaS の UI/UX 設計と UX ライティングのノウハウ（`docs/ui-ux-writing-guide.md`）が提供された。機能を「文脈・頻度・危険性・次の行動」の 4 軸で観察して配置し、文言はボイス&トーン 1 ページ・用語集・一元管理・レビューの 2 問・実物で読む、で仕組み化する、という内容

## 決定
- **摩擦は危険性に比例させる**（`console/UX.md` の 4 軸の表が正本）
  - 可逆（状態を進める・戻す、種別や PR を直す）: 確認を出さない。トーストに「元に戻す」を置く。元に戻す = `kb set --status <前の状態>`
  - 半可逆・影響大（本番 run、配車）: 自前の `<dialog>` で、何を・どこで・どれくらいかかるかを名前と数字で見せる。配車は押す前に **次に回るチケット**（`kb next --json`。`GET /api/next`）を出し、未着手が無ければ押せない
  - 不可逆・影響大（VM の返却、ジョブの停止）: 危険色のダイアログ、既定フォーカスはキャンセル。その VM で run が動いていれば **チケット番号の入力**を求める
  - dry-run は本番のボタンから離し（破線の下の ghost ボタン）、危険なボタンを頻用ボタンの隣に置かない
- **操作の後を設計する**: ジョブが終わると「次にすること」を 1 つのプライマリと数個のセカンダリで出す（intake → できたチケットを開く / run 停止 → 状態を実行記録に合わせる / 返却 → sandbox を見る）。状態を変えたら印を光らせる
- **頻度で配置する**: ナビは頻度順（ボード / 起票 / 実行記録 / ジョブ / sandbox / ログ / 設定）。配車はボードのダイアログへ、「取り込み」は「起票」に。毎日使う画面には `g` + 頭文字の近道
- **文言は `static/strings.js`（`T`）に集める**。`app.js` に日本語を直書きしない。本体は厳密な JSON で、`tests/test_strings.py` が CI で検査する: 補助動詞のひらがな・二重敬語・責める言葉・開発者の語彙・用語のゆれ（タスク / プロジェクト）・感嘆符・全角英数字を弾き、ボタンは動詞で終わること、文は「ですます」で「。」で終わることを見る。`app.js` / `index.html` が参照する鍵と `strings.js` の鍵が一致すること（未定義も未使用も落とす）
- 用語集とボイス&トーンは `console/UX.md` の 1 ページに収める。同じ概念は画面・CLI・ドキュメントで同じ言葉（チケット / PJ / 実行記録 / 工程 / ジョブ / 貸出）。`#` は PR 番号にだけ使い、チケットは「チケット 204」
- サーバー側（`lib/core.py` / `bin/console`）の `ApiError` の文も「何が起きたか + どうすればよいか」に揃える。MCP からも同じ文が返る

## 理由
- 確認ダイアログの乱発より「取り消し可能性」のほうが体験もエラー率も良い、という HCI の一貫した知見（ノウハウ第 1 部 3）。可逆な操作から確認を外し、その分を不可逆な操作の摩擦に回す
- 「どれが押されるか」を先に見せるのは、影響範囲を数字と名前で示す原則の直接の適用。配車は「未着手の最も古い 1 件」という規則が人の頭の中にしか無かった
- 文言を 1 か所に集めるのは、表記のゆれが「個人のセンスに任せると必ず崩れる」ため。textlint を入れると npm が要り、ADR-0013 の「標準ライブラリだけ」が崩れる。同じ検査を Python の unittest で書けば CI にそのまま乗る
- 標準の `confirm()` を自前の `<dialog>` に替えるのは、ボタンに動詞を書く（「削除しますか？ はい / いいえ」を避ける）ため。`confirm()` は「OK / キャンセル」しか出せない

## 結果（トレードオフ）
- 良い: 状態の変更が 1 クリックで済み、間違えても戻せる。返却の誤操作はチケット番号を打たない限り起きない。intake → チケット → 実行 → 実行記録の流れが、各画面の「次にすること」でつながる
- 良い: 文言の追加・変更が `strings.js` 1 ファイルで済み、CI が表記を見る。英語化するときも同じ形で `strings.en.js` を置ける
- 悪い: `app.js` が `T.a.b` の参照で読みにくくなる。テンプレートの中に文が見えない
- 悪い: 検査は正規表現なので、文法上は正しい文を弾くことがある（`tests/test_strings.py` の TERSE_END を直す）。逆に、丁寧でない文を通すこともある。レビューの 2 問（ボタンだけで結果が分かるか / エラーで次が分かるか）は人がやる
- 悪い: 元に戻すは 8 秒のトーストの間だけ。それ以降はチケット画面の「状態を進める」で手で戻す（`kb history` に両方残る）
- 実測（2026-09-07）: unittest 31 本（console 20 本 + MCP 6 本 + strings 5 本）。複製 workspace でボード / チケット / 配車ダイアログ / 返却ダイアログ / 元に戻す / 次にすること / 近道をブラウザで確認
