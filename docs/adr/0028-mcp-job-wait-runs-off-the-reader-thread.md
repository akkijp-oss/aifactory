# ADR 0028: MCP の `job_wait` は読み取りスレッドから外して待つ

- 状態: Accepted
- 日付: 2026-09-08

## 決定

`console/bin/mcp` の読み取りループは、`tools/call` のうち **待つだけのツール（今は `job_wait` だけ）** を daemon スレッドに逃がし、それ以外は今までどおり到着順に直列で処理する。応答の書き出しは `reply()` に一本化し、lock の中で write と flush をまとめて行の混線を防ぐ。

`job_wait` の `timeout_s` は **既定 60 秒・上限 300 秒**（ADR-0015 の「上限 570 秒」を改める）。終わらなければ `state` が `running` のまま返るので、長く待ちたい呼び出し側は繰り返し呼ぶ。

逃がしてよいツールは `ASYNC_TOOLS` に明示する。ここに `ticket_run` / `intake` 等を安易に足さない。

## 理由

`main()` が 1 行読む → `handle()` を同期で呼ぶ → 応答を書く、の直列ループだったため、`core.job_wait()` がポーリングしている間は次のリクエストを **読みもしなかった**。実測（2026-09-08）で `job_wait(timeout_s=570)` の後の `ticket_run` / `ticket_action` / `job_show` が約 10 分間実行されず、2〜3 本の run を並行して見る使い方だと MCP が実質 1 本ずつしか使えなかった。

`job_wait` だけを逃がすのは、待つ以外に何もしないツールだから。読み取り系・状態変更系を直列のまま残せば、同じチケットへの `ticket_action` の到着順がそのまま守られ、追加のロックが要らない。`core` 側は既に ThreadingHTTPServer から多スレッドで呼ばれており（`rows()` は都度接続、`JobStore` は lock + flock）、スレッド安全性の前提は変わらない。

上限を 570 → 300 秒に下げるのは、Claude Code が 120 秒でツール呼び出しをバックグラウンド化するため、それ以上待たせても呼び出し側に届く形にならないから。

## 制約

- daemon スレッドなので、stdin が EOF（クライアントがサーバーを閉じた）になれば `job_wait` の待ち中でもプロセスは今までどおり終わる
- 応答の順番は到着順とは限らなくなる。JSON-RPC は `id` で対応づける仕様なので問題ないが、テストで応答を読むときは `id` を見る
- `timeout_s=570` を渡す既存の呼び出し側は、エラーにはならず 300 秒で `running` のまま返る
- `notifications/cancelled`（クライアント側の打ち切り）は今までどおり無視する。待ちスレッドは timeout まで残る
