# ADR-0012: glue は「取り込み（LLM 1 回）」と「配車（ただのコード）」の 2 本。ステップ間の状態は runner に任せる

日付: 2026-09-06 / 状態: 採用 / 決定者: メンテナ（「それらを前へ進めましょう」で着手指示）

## 状況
- kanban（ADR-0011）で採番・状態・本文が揃い、runner v1 が `kb run` から回るようになった。残る空白は「自由文の依頼をチケットにする」と「todo を自動で回す」の 2 つ
- 動画の構図: Kanban は「ただのコード」、その先のルーターは「簡単な LLM 呼び出し 1 回か決定的なコード」、各ステップの間の結果を置く場所が要る
- glue の当初の役割定義（`glue/README.md` 旧版）は「ルーター・ステップ間の状態・ログ」の 3 つだった。ステップ間の状態は runner v1 が `~/work/<task>/` と `state.json` で既に持っている

## 決定
- **intake**（`glue/bin/intake`）: 自由文 → 1 枚のチケット。先頭の `pj:` / `kind:` 行や `--pj` / `--kind` があれば決定的に採用し、決まらない分の判定と整形（題名・完了条件）を judgment クラスのモデルに **1 回だけ** 聞く。出力は提案で、`kb new` が pj / kind の実在を検証する。confidence とモデル名を本文末尾に残す
- **dispatch**（`glue/bin/dispatch`）: todo を古い順に取り、`project.yml` の有無とプールの空き（PJ あたり 3 台）だけを見て `kb run` する。判断はしない。直列
- **ステップ間の状態は glue に作らない**。runner の artifact 回収と `state.json` を正とする。glue のログは起票（`intake.log`）と配車（`dispatch.log`）だけ
- LLM は Mac 側の `claude -p` をツール無し・一時ディレクトリで呼ぶ。VM は使わない（VM はタスク実行専用）

## 理由
- ルーターを「LLM 1 回」に留めると、失敗の切り分けが簡単になる（判定が違えば `kb set` で直すだけ。以降はコードの経路）
- 種別の情報を kanban に持たせ dispatch を無判断にすることで、dispatch は cron や手動で何度呼んでも同じ結果になる
- ステップ間の状態を二重に持つと、どちらが正か分からなくなる。runner に既にあるものを使う
- 決定的な指定（`pj:` 行）を LLM より優先するのは、人間が分かっていることを推測させないため

## 結果（トレードオフ）
- 良い: 自由文からの起票が 20 秒、配車は無人。失敗点が「判定」「実行」に分かれて読める
- 悪い: dispatch が直列なので、ゲートが 60 分の run が 1 本あると他が待つ。並列化は PJ 単位のプールが別なので可能だが、まずゲートの差分実行を先にやる
- 悪い: project.yml の無い PJ は `blocked` になる。project.yml を書くまで自動では回らない
- 実測（2026-09-06）: Rails + MySQL の PJ の seeds 不具合を自由文から起票（confidence 0.9、bug）、別 PJ の e2e 不具合は `project.yml` 無しで blocked、dispatch の dry-run は runner まで到達
