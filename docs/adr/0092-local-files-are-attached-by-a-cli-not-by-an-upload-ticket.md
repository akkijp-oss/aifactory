# ADR 0092: 手元のファイルは「ローカルの CLI が既存の multipart API へ直接送る」で添付する。一時アップロード領域（`upload_id`）は作らない

- 状態: Accepted
- 日付: 2026-09-16
- 関連: ADR-0041（添付は `kanban/attachments/<id>/` に置き、本文には書かない）、ADR-0015（判定は lib に 1 か所）、
  ADR-0017 / ADR-0021（MCP は ctl の中で動く / コンソールは内側の網に出せる）、#596

## 状況

添付の入口は 3 つある。`kb attach`（CLI）、`POST /api/tickets/<id>/attach`（multipart）、
MCP の `ticket_attach`（`content_base64` / `path`）。どれも `lib/aifactory_attachments.py` を薄く呼ぶだけで、
書き込みは必ず `kb attach` を通る（履歴と一覧が揃う経路）。

利用者が求めているのは「**ファイルの中身を LLM のコンテキスト・ツール出力・通常ログに通さずに添付する**」こと。
今の 3 つでは次のとおり満たせない。

- `ticket_attach(path=...)` の `path` は **ctl（制御系 LXC）の上のパス**である。MCP のプロセスは ctl の中で動き、
  `console/bin/mcp-remote` は ssh の stdio を中継するだけでファイルを運ばない（ADR-0017）。利用者の手元 PC の
  ファイルは読めない。
- `ticket_attach(content_base64=...)` は中身を MCP の引数に載せる。コード内で組み立てれば LLM の文脈に出さずに
  済むが、引数・ログ・再試行のたびに本体が JSON-RPC の 1 行として流れる。
- `POST /api/tickets/<id>/attach` は元々 tailnet 経由で**利用者の端末から直接届く**設計（ADR-0021）だが、
  リポジトリに multipart を**組んで送る側**の実装が無く、利用者は curl を手書きするしかなかった。

#596 は「一時アップロード API（`POST /api/uploads`）で `upload_id` という手形を発行し、起票後にその手形で
紐づける」という案（案 A）で起票された。

## 決定

1. **手元のファイルの添付は `console/bin/attach`（ローカルで動く CLI）が `POST /api/tickets/<id>/attach` へ
   直接 multipart で送る**。受け口・保存・履歴・runner への配布は既存のまま何も変えない。

2. **一時アップロード領域と `upload_id` は作らない。** `POST /api/uploads` も、手形の有効期限も、期限切れの
   自動削除も、手形の冪等・再利用規則も本 PR では実装しない。必要になったら別 ADR で足す。

3. **CLI は判定を持たない。** 1 ファイル / チケット合計の上限も名前の sanitize も
   `lib/aifactory_attachments.py` が正本（ADR-0015）。CLI は事前に判定せず、断るのは server 側で、
   利用者に見せる文面も server のものをそのまま出す。保存された名前は応答の `added` で返る。

4. **CLI の出力は小さなメタデータだけ。** 成功時は応答の JSON（`id` / `added` / `attachments`）を stdout に
   1 行。失敗時は理由 1 行を stderr に出して非 0 で終わる。**ファイルの中身・その base64・合言葉・
   `Authorization` ヘッダはどの出力にも出さない**。出力の長さはファイルの大きさに比例しない。

5. **合言葉（`CONSOLE_TOKEN`）は argv で受けない**（`ps` に出るため）。環境変数か
   `~/.config/aifactory/mcp-remote.env`（`mcp-remote` と同じ手元の設定ファイル）から読む。接続先は
   `AIFACTORY_CONSOLE_URL`（既定 `http://127.0.0.1:8765`）。

6. **既存 3 方式は無改修**。`multipart` 直叩き・`content_base64`・`path` は今までどおり動く。MCP の
   `ticket_attach` は説明文に「手元 PC のファイルは `console/bin/attach` で送る」を足すだけで、引数も判定も
   変えない。

## 理由

- **主目的は案 B（CLI だけ）で完全に達成できる。** 本体は端末から HTTP へ直接流れ、LLM は番号とパスと
  小さな応答しか見ない。手形を挟んでも「LLM に本体を通さない」という性質は 1 ミリも良くならない。
- **案 A は判断を 4 つ増やす。** 手形の有効期限、期限切れの掃除、同じ手形の再送（冪等）、別チケットへの
  再利用可否。これらは「起票前にアップロードしたい」場合にだけ要る。起票は `kb new` / `ticket_new` で
  数秒で済み、既存の運用は「起票 → 番号で添付」（`kb new --attach` と同じ順）で回っている。
- **掃除は事故の余地を作る。** 「未添付の実体を期限で消す」機構は、添付済みの実体を誤って消す経路を
  新しく開く。並行する添付と掃除の競合も自前で守ることになる。今は誰も困っていない問題のために、
  消える側のリスクを買わない。
- **使われない API を残さない。** 中途半端に `POST /api/uploads` だけ作ると、誰も呼ばない口が
  ルーティング表と文書に残り、後から消す票が要る。
- **CLI に判定を書かない**のは、上限の数値が lib と CLI の 2 か所になると必ずずれるから（ADR-0015 の型）。
  事前に弾けないぶん大きいファイルは一度送ってから断られるが、上限は 20 MiB で、送ってから断る方が
  「二重の正本」より安い。

## 結果

- 手元の端末で `console/bin/attach <チケット番号> <ファイル>...` が使える。AI セッションは、この 1 行を
  利用者に案内するか Bash から呼ぶだけで、本体を扱わない。
- #596 の完了条件のうち `upload_id`・有効期限・自動削除・手形の冪等・別チケットへの再利用に関わるものは
  **本 ADR では満たさない**（段階 2）。要る根拠（起票前アップロードが必要な実例）が出たら別票・別 ADR で
  起こす。その際も本 ADR の決定 3・4 は引き継ぐ。
- CLI が組んだ multipart を受け口（`parse_multipart`）がそのまま解けること、実体が元ファイルと
  バイト単位で一致すること、出力が漏らさないことは `console/tests/test_attach_cli.py` が固定する。
- **利用者の実端末から tailnet 経由で ctl のコンソールに届くこと**は、実装環境（`browser` / `gui` を
  持たない sandbox VM、ADR-0080）では確かめられない。127.0.0.1 の console に対する結合テストまでが
  この ADR の検証範囲で、実経路の確認は着地後に手元の端末で行う。
