# ADR 0090: 鍵残量の観測は「非可逆な指紋で世代を見分け、未知の枠ヘッダは生のまま控え、枯渇は `rejected` だけ」とし、1 周はファイルロックで直列化する

- 状態: Accepted（ADR-0087 の観測を足す。ADR-0087 は書き換えない。観測の経路・周期・語彙・stale の判定（ADR-0087 と #616）は変えない）
- 日付: 2026-09-16
- 出どころ: #559 の調査（本 VM の注入鍵で実測）が残した申し送りのうち、ADR-0087 の実装に入らなかった 4 点

## 状況

ADR-0087 で鍵プールの残量を 5 分ごとに観測して「鍵」画面と `keys_list` に出せるようになった。運用に入る前に、#559 の調査が実測で見つけて申し送った 4 点が手つかずで残っている。

1. **世代の見分けが末尾 4 文字しかない。** `run_probe()` は前回の `tail4` と違うときだけ履歴を捨てる。同じ名前に**末尾 4 文字が同じ別のトークン**を入れ直すと（同名再登録や、たまたま末尾が一致した交換）、別の契約の残量と履歴が混ざったまま続く。さらに、プローブは 1 本あたり数秒かかるので、**叩いている間に console から鍵を交換・無効化・削除されても**、戻ってきた前の鍵の応答をそのまま新しい鍵の残量として保存してしまう。
2. **意味の分からないヘッダを捨てている。** #559 は実測で `anthropic-ratelimit-unified-reset`（窓別ではない単一の値）と `anthropic-ratelimit-unified-fallback-percentage`（値 `0.5`）の 2 つを見つけた。どちらも公式文書に無く、aix にも ADR-0087 の実装にも読み取りが無い。読まないと履歴も残らないので、後で意味が分かったときに遡れない。
3. **枯渇の判定に根拠の無い閾値がある。** `window_summary()` が `utilization >= 0.99` を枯渇とみなし、`remaining_pct` を 0.0 に潰していた。0.99 という数字の出どころは無い。残り 1% の鍵はまだ使えるのに「枯渇（回復待ち）」に見え、逆に**使用率が低いのに `rejected` な窓**（組織側の制限など）は枯渇として扱われない。
4. **timer と手動の排他が無い。** systemd の timer は `lib/aifactory_keys_quota.py probe` を直接実行し、console の JobStore を通らない。console 側の「実行中なら起こさない」判定も JobStore のロックの外にあり（他の 4 か所は `conflict=` でロックの中）、同時に押されると 2 本起きる。重なると同じ鍵に二重の課金プローブが飛び、応答の順序が逆転すると新しい値が古い値に巻き戻る。

`unified-*` のヘッダ群は**非公開・非文書化**で、公式の statusline（対話セッション内でしか出ない）でも公式の rate-limits ページ（従量制のトークンバケットで、サブスクの利用枠ではない）でも代わりにならない。#559 の結論は「補完経路は無い」。つまりこの一本足が折れたら残量は取れなくなる。

## 決定

1. **世代はトークンの非可逆な指紋で見分ける。** `fingerprint(token) = sha256(token) の先頭 16 桁`。`key_quota.fp` に置き、前回の指紋と違えば履歴ごと捨てる（`forget()`）。指紋を持たない古い行は今までどおり `tail4` で比べる（後方互換）。**指紋は DB の内部列にしか置かない** — `view()` / `/api/keys` / `keys_list` / CLI / ジョブの記録には出さない。`keys.json` の `issued` は日付粒度で同日の再登録を区別できないので採らない。
2. **観測中に鍵が変わった回は捨てる。** `probe()` から戻った直後に `keys.json` を読み直し、その名前の鍵が消えている / 無効になっている / 指紋が変わっているなら `record()` せず、`skipped` に `removed-during-probe` / `disabled-during-probe` / `replaced-during-probe` として残す。次の周で `forget()` が効いて履歴が切り替わる。
3. **知らない `anthropic-ratelimit-unified-*` ヘッダは生のまま別テーブルに控える。** `key_quota_raw(name, header, value, probed_ts)` に、読めた回だけ 1 ヘッダ 1 行。**表示にも判定にも使わない** — `summarize()` / `view()` / `history_view()` / CLI `show` はこのテーブルを読まない。読むのは診断のときだけで、`sqlite3 <DB> "select * from key_quota_raw"` か `Store.raw()`。接頭辞 `anthropic-ratelimit-unified-` の外は**絶対に控えない**（名前 80 文字・値 200 文字・1 応答 20 本で切る）。2 つを名指しの列にしないのは、#559 が言う「Fable 許可の無い鍵に `7d_oi` 相当の未知ヘッダが出たら拾う」も同じ仕組みで自然に拾えるため。
4. **枯渇（`exhausted`）は窓の `status == "rejected"` だけ。** 使用率がいくら高くても、API が断っていないなら枯渇ではない。`remaining_pct` は常に `round((1 - utilization) * 100, 1)` で、`rejected` の窓でも実測の数値をそのまま出す（reject 状態と数値を別々に扱う）。「あと何 % で警告か」は表示側の閾値（「鍵」画面の 10% / 25%、CLI は 10% 未満を小数 1 桁）に残す。`binding`（いちばん逼迫している窓）は**断られている窓を最優先、次に残量の少ない順**で選び、`binding.exhausted` でどちらか分かるようにする。
5. **1 周はプロセス間のファイルロックで直列化する。** `<DB>.lock`（DB の隣・600）に `flock`。取れなければ 1 本も叩かずに `locked: True` で返り、CLI は rc 0（timer が赤くならない。重なりは失敗ではない）。`probe --wait SEC` で最大 SEC 秒待てる。console の「いま調べる」は `--wait 120` を付けて timer の後ろに並ぶ（手動は必ず新しい値が欲しい）。あわせて `Store.record()` に巻き戻り防止を入れる: 最後に読めた時刻より前の観測では現在値を更新しない（履歴と控えには事実として残す）。console 側の `keys_probe()` は他の 4 か所と同じ `JobStore.start(..., conflict=)` に揃える（判定をロックの中でやる）。
6. **既存 DB への移行は「列を足す」だけ。** 書き込み側（`Store.__init__`）が `PRAGMA table_info` を見て足りない列を `ALTER TABLE ... ADD COLUMN` する。読み取り専用（console）は移行しない — 古い DB を読んでも新しい列が無いだけで壊れない。列の削除・改名・型変更はしない。

## 理由

- **なぜハッシュで、値を持たないか。** 世代の識別に要るのは「同じか違うか」だけで、元の値は要らない。DB は `keys.json` と同じ場所・同じ 600 なので指紋が漏れる経路は `keys.json` 本体と同じだが、それでも**外に出す面（API / MCP / CLI / ログ）を 1 つも増やさない**ことで、ADR-0087 の「名前と末尾 4 文字より先を出さない」を保つ。
- **なぜ未知ヘッダを捨てないか。** `unified-*` は非公開・非文書化で、仕様変更の予告が無い。今読めている値が明日消えるかもしれず、いま意味の分からない値が明日の手がかりかもしれない。控えるのは安い（1 応答で数行）。ただし**意味が分かるまでは表示にも判定にも使わない** — 意味を推測して画面に出すと、根拠の無い数字が人の判断に入る。
- **なぜ接頭辞の外を控えないか。** ヘッダには `authorization` の写しや追跡 ID が載りうる。「外から返る文字列を無条件に記録しない」を守るには、拾う範囲を先に狭く決めるのが唯一確実な方法。
- **なぜ 0.99 をやめるか。** 閾値は**表示の都合**（そろそろ危ない）であって**事実**（もう使えない）ではない。事実は API が `rejected` と言ったかどうかで、それは観測できる。サーバー側で潰すと、残り 1% という事実が誰からも読めなくなる（履歴にも 0% として残る）。
- **なぜ鍵単位でなく 1 周ごとのロックか。** 1 周は十数秒、周期は 5 分。鍵ごとの粒度を足しても防げる二重叩きは変わらず、ロックの数だけ増える。1 本のロックで済む。
- **なぜ DB 本体でなく隣の `.lock` か。** SQLite は自分でファイルをロックする。同じファイルに別の流儀のロックを重ねると、どちらの都合で待っているのか読めなくなる。
- **なぜ timer 側は待たないか。** 5 分ごとに来るので、重なった回は飛ばしても次が来る。待たせると timer のプロセスが溜まる。手動は人が押して結果を見ているので待つ。

## 結果

- 同じ末尾 4 文字の別トークンに入れ替えても、前の契約の残量と履歴を引き継がない。観測中に鍵をいじっても、前の鍵の応答が新しい鍵のものとして残らない（その回は `skipped`）。
- `keys-quota.db` に `key_quota.fp`（内部列）と `key_quota_raw`（未知ヘッダの控え）が増える。どちらも既存 DB に自動で足され、剪定（既定 30 日）と `forget` / `keep_only` の対象。
- 「残量」の数字が変わる: 使用率 99.5% の窓は「枯渇」ではなく「残り 0.5%」と出る。逆に使用率が低くても `rejected` の窓は枯渇として `binding` に上がる。画面の赤・橙の閾値（10% / 25%）は今までどおり。
- timer と「いま調べる」と手元の CLI が重なっても、同じ鍵を二重に叩かない。重なった回の CLI は「別のプローブが実行中」と言って rc 0 で終わる。
- 対象外（触らない）: 観測の経路・モデル ID・周期（ADR-0087 の 2）、`probed` / `ok` / `status` の語彙、`stale` の判定基準（#616）、**窓ごとの鮮度**（`7d_oi` の古さは今までどおり `fable_probed` と `ok` の差でしか分からない。構造を変えるなら別の決定にする）、401 / 403 の意味づけ（今までどおり `error` 文字列に落とすだけで「鍵失効」と断定しない）、鍵の選び方（ADR-0044）、macOS / launchd（keys-probe 固有ではなく全 timer に plist が無い既存のギャップ）。
- テスト: 指紋（同末尾の別トークン・同じトークン・省略時の据え置き・外に出ないこと）、観測中の交換 / 無効化 / 削除、未知ヘッダ（拾う範囲・上限・失敗回は控えない・表示に出ない・剪定と `forget`）、枯渇（高使用率は枯渇でない・`rejected` は数値を保ったまま枯渇・`binding` の順序・リセット待ちの除外）、排他（握られている間は 0 本・`--wait`・解放後は走る・巻き戻り防止）、旧 DB の列追加、console の `POST /api/keys/probe` の二重起動。
