# ADR 0081: 掃き寄せは**救済**であって成果物の判断ではない。依存ファイルは拾わず、拾ったものは必ず記録に残す

- 状態: Accepted
- 日付: 2026-09-16

## 状況

runner は step の終わりに、作業ツリーに残った**追跡済み**の未コミット変更を
`sandbox: uncommitted changes by agent` という**本文ゼロ**のコミットで拾う（`workflow/bin/run` の `commit_tracked()`）。
`git add -u` なので未追跡（生成物・DB）は既に除外されている——過去に `git add -A` が生成物を拾った事故の対処である。

残っていたのは「**追跡済みなら何でも拾う**」ことだった。kumitate で次が起きた（チケット 572）。

- **#527 / PR#401**: 掃き寄せが `apps/kumitate/apps/web/package.json` の `@types/node` を `^22.20.2` → `^20.17.6` へ
  下げ、`pnpm-lock.yaml` を 199 行書き換えた。PR は該当のコンポーネントに触っていないのに、CI の `test:dom` が
  **18 件赤**（Node 20 の型では vitest の snapshot client が初期化できない）。
  ★**VM の gates は緑だった**（`node_modules` が既に入っているので影響が出ない）。gates 緑は CI 緑を保証しない。
- **同じ汚れが次の便の VM に残っていた**（#542 の planner が着手前に検知）。run 開始時に作業ツリーの清浄性を
  確かめる経路が 1 つも無く、汚れた木が次の run の基準（baseline）になっていた。
- **1 日 6 便中 5 便で再発**。検知は planner 2 回・実装役 1 回・reviewer 2 回の**計 5 回すべて成功**し、
  **阻止は 0 回**。#542 と #574 は review FAIL の**唯一の理由**が掃き寄せで、実装本体はどちらも「計画どおり・範囲内」だった。
- 下流の診断まで腐った。管理役はこの赤を develop 自身の欠陥と読み違えて**存在しない欠陥の票（#575）を起票**し、
  訂正に 3 往復かかった。`known_red_gates` に汚れた測定が載った疑いも残った。

つまり **検知と阻止は別物**で、阻止は下流の注意深さではなく機構の仕事である。

## 決定

1. **掃き寄せの役割を「救済」に限定する。** step が時間上限・利用枠で切られたとき、未コミットの実装を
   次の attempt へ渡すためのものであって、「成果物に何を載せるか」の判断ではない。**廃止はしない**
   （救済が無いと、切られた step の作業が release で消える。チケット 329）。

2. **意図の確認が取れない依存ファイルは拾わない。** 既定で `**/package.json` と `**/pnpm-lock.yaml` を
   掃き寄せの対象から外し、**作業ツリーごと HEAD の内容へ戻す**。戻すのは、gates と reviewer が測る木と
   push する木を一致させるため（片方だけ直すと、次の便がまた同じ地雷を踏む）。
   既定に入れるのはチケット 572 が**実データで名指しした 2 つだけ**。npm / yarn / uv の lock を足すかは、
   過去の run が実際に何を拾ってきたかを集計してから決める（推測で増やさない）。

3. **意図した依存の変更は実装役が自分でコミットする。** 役割文書に「コミットは自分で行う」と既にある。
   実装役が自分で `git add` したファイルは除外の対象にしない（意図が明示されている）。
   **票ごとの切替は作らない**——「この票は依存を変えてよい」というフラグを増やすと、掃き寄せが再び
   「何を載せるか」を判断する場所に戻る。PJ 単位の `sweep_exclude`（`project.yml`）だけを口にする。

4. **拾ったこと自体を記録に残す。** 掃き寄せコミットの**本文**に拾った一覧と除外して戻した一覧を書き、
   `state.json` の工程履歴に `swept` を、`run_outcome` に `swept` を載せ、runner の標準出力にも 1 行出す。
   これまでは**差分を開くことだけ**が気づく手段だった（#527 はそれで PR まで載った）。

5. **run の開始時（checkout の直後と `prepare` の直後）に作業ツリーの清浄性を確かめ、汚れていれば HEAD へ戻す。**
   未追跡は触らない。**run は止めない**（テンプレート起因なら全便が止まるため。票の (a) 掃除 + 記録を採り、
   (b) だけにはしない）。戻した事実は `state.json` の `dirty_at_start` と `outcome` に残す。
   これは除外リストとは**独立に**効く（除外を入れても、汚れが残っていること自体が偽の baseline と誤診を生む）。

6. **規則の正本は `lib/aifactory_sweep.py` の 1 か所。** `workflow/bin/run`（Linux/proxmox）と
   `workflow/lib/windows.py`（PowerShell）は pathspec と文面をこの lib から読むだけで、glob も文言も自分で持たない
   （ADR-0080 の `lib/aifactory_capabilities.py` と同じ形。写しを 2 か所に置くと片方だけ直る）。

## 影響

- 環境が書き換えただけの lock / manifest は PR に載らなくなる。gates と reviewer は develop と同じ依存で測る。
- **意図した依存の変更を実装役が未コミットのまま終えた場合、その変更は PR に載らない。** これは受け入れる:
  役割の約束（自分でコミットする）で担保し、除外した一覧を本文・stdout・`outcome` の 3 か所に出すので気づける。
- `workflow/lib/windows.py`（PowerShell 版）は**除外と本文まで**寄せた。除外したファイルを戻す所と `swept` の記録は
  実機で確かめられないので入れていない（別票）。`workflow/bin/spin-v0.sh` の v0 は対象外。
- 票が挙げた `engines.node` との矛盾検査と lockfile の生成器（`libc:` 行の消失）検査は**別の機構**なので、本 ADR には含めない。
  除外 + 記録 + 開始時の清浄化で、その 2 つが狙う事故（意図しない依存変更の混入）は塞がる。

## 代替案

- **掃き寄せを廃止する**: 時間上限で切られた step の作業が消える（チケット 329 が入れた救済を失う）。採らない。
- **汚れていたら run を止める**: テンプレート起因なら全便が起動直後に止まる。可視化と復旧を優先し、止めない。
- **除外を `run` と `windows.py` に直接書く**: 規則が 2 か所になり、片方だけ直る（#578 の写し検査が示した型）。採らない。
