# ADR 0073: console から直せるのは「その工程の yml ブロック 1 つ」まで。id と担い手の種類は固定する

- 状態: Accepted
- 日付: 2026-09-14
- 置き換え: [ADR-0065](0065-console-edits-model-settings-in-the-work-tree.md) の**決定 4 の「工程は `model` と
  `model_class` のみ」**と、**決定 5 の「当該 1 行だけを差し替え」**。決定 4 の残り（`routes.env` の範囲・値の形・
  鍵の系統の検査・鍵プールが空でも止めない・**任意のファイル編集の口にはしない**）と、決定 5 の検査の 2 条件・
  書く順番（検証 → 退避 → 一時ファイル → `os.replace`）、決定 6（競合）・決定 7（実行中の run）は、そのまま生きている。
  [ADR-0072](0072-console-picks-a-model-by-display-name.md) の 2 段の選び方も変えない。

## 状況

工程詳細（`#/config/workflow/<name>/<stepId>`）で変えられたのは、フォームの `model` と `model_class` の 2 つだけだった
（`console/lib/core.py` の `STEP_MODEL_KEYS`）。

工程にはほかに `timeout_min` / `next` / `on_pass` / `on_fail` / `inputs` / `outputs` / `brief` があり、画面で**読めるが変えられない**。
変えたい運転員は制御系に入って yml を手で直すことになり、ADR-0065 が解こうとした問題
（手で直すと変更前後の実効値・影響する工程・動いている run への影響が誰にも見えない）が、そこだけ残っていた。

「変えられるキーを 1 つずつ足していく」で広げると、キーの数だけフォームの欄・保存の枝・検査が増える。
`on_fail: { goto, max_loops, else }` のような入れ子まで欄にすると、定義の書式を画面に写し取ることになり、
schema と画面で二重管理になる（ADR-0062 / ADR-0072 が避けてきた形）。

## 決定

1. **編集の単位を「その工程の yml ブロック 1 つ」にする。** 画面はその工程の `- id: <工程>` の行から、次の工程が始まる
   直前までの**原文**を `textarea` に出し、運転員はそれを直す。`POST /api/config/model` に `target: "block"` を足す。
2. **ファイル全体は出さないし、書けない。** 書き先は今までどおり `workflow/kit/workflows/<name>.yml` だけで、
   1 回の保存で変わるのは当該工程のブロックだけ。ADR-0065 決定 4 の「任意のファイル編集の口にはしない」はここで生きている。
   境界の定義は 1 か所（`core.step_block_bounds`）に置き、1 キーの差し替え（`yaml_step_edit`）と共用する。
3. **工程の `id` は変えられない。** 送られたブロックの 1 行目が `- id: <元の工程>` でなければ 400。
   ほかの工程の `next` / `on_pass.goto` / `on_fail.goto` がこの `id` を指しているが、**参照の整合を検査する仕組みは
   schema にも lib にも無い**。id を書き換えられるようにすると、他工程からの行き先が黙って迷子になる。
4. **担い手の種類（`role` か `code` か）も変えられない。** `role` の工程は `role` を持ったまま、`code` の工程は
   `code` を持ったまま。違えば 400。`role` の値（`planner` → `reviewer` など）は schema の enum の中で変えてよい。
   種類が変わると、その工程がモデルを使うかどうか（ADR-0065 決定 8）ごと入れ替わる。それは定義そのものの設計変更で、
   1 工程のブロックを直す操作の範囲ではない。
5. **「当該ブロック以外が 1 文字も変わっていない」を、比較ではなく組み立て方で保証する。** 書く本文は必ず
   `旧本文の [0, item) 行 + 新しいブロック + 旧本文の [end, len) 行` で作り、書く前に前半・後半がバイトで一致することを見る。
   `yaml.safe_load` はコメントを捨てるので、**dict の比較ではコメントが保たれたことを言えない**。pyyaml で書き戻す道は取らない。
6. **書く前の検査を、1 キーのときより強くする。** 落ちたら 1 バイトも書かない（`os.replace` に到達しない）。
   (a) 1 行目が `- id: <元の工程>` である (b) yml として読める (c) 工程の並びと id の列が元と同じ
   (d) 当該工程以外の工程の dict が元と完全一致 (e) `steps` 以外のトップレベルのキーが元と完全一致
   (f) 担い手の種類が元と同じ (g) `model` を変えたなら鍵の系統が分かる（ADR-0065 決定 4 の `check_model_name`）
   (h) 変更後の本文全体が schema に適合する（`additionalProperties: false` なので未知キーもここで落ちる）
   (i) 新しい本文で境界を取り直しても同じ 1 工程を指す。受け取るブロックの上限は 64 KiB。
7. **保存の流れは今までと同じ。** 下見（既定）→ 変わるキーの前後・影響する工程の実効モデル・動いている run →
   確認 → `base_sha256` 付きで保存 → `.bak-<時刻>` に退避 → `logs/config-changes.jsonl` に 1 行。
   記録にはブロックの原文を丸ごと残さず、**変わったキーだけ**を前後つきで残す。
8. **フォームと yml の欄は画面の中だけで同期する。** サーバー往復はしない。同期するのは `model` と `model_class` の 2 行だけ
   （フォームにあるのがその 2 つだから）。ほかのキーは yml の欄でだけ直す。
9. **yml の欄は `code` 工程にも出す。** ADR-0065 決定 8 の「入口を出さない」は**モデルの欄**の話で、
   分岐・時間の上限は機械が回す工程にもある。モデルの欄は今までどおり `code` 工程には出さない。

## 理由

- **なぜ「キーを 1 つずつ足す」ではなくブロックごとなのか。** 足すたびに欄・保存の枝・検査・文書が増える。
  ブロックごとなら、増えるのは「範囲の検査」1 組だけで、schema がすでに持っている「何を書いてよいか」をそのまま使える。
  定義の書式の正本は `workflow.schema.json` の 1 か所のままになる。
- **なぜ `id` を固定するのか。** 参照整合の検査を持たないまま id を可変にすると、保存はできるのに次の run が
  「行き先の工程が無い」で止まる。壊れたことが分かるのが**保存の 3 日後**になる。検査を新設する手もあるが、
  それは ADR-0065 の「書けるのは許可した設定だけ」を広げる別の判断で、この決定には入れない。
- **なぜ担い手の種類を固定するのか。** `role` と `code` は schema の `oneOf` で排他なので、入れ替えても**形としては通ってしまう**。
  通るが、その工程は鍵も割り当たらず brief も読まれない別物になる。1 工程の設定を直す画面で起こしてよい変化ではない。
- **なぜ前後のバイト一致で保証するのか。** チケットの完了条件が「コメント・並び・引用が保存後も保たれている」だから。
  これを dict の比較で言おうとすると、コメントを保つ yaml ライブラリ（ruamel）が要る。入れていないし、
  入れても「1 文字も変わらない」は言えない（引用の正規化が起きる）。触っていない行を**物理的に触らない**のが一番強い。
- **なぜブロックの中のコメントは守らないのか。** 守る必要が無い。運転員が `textarea` で見ているものがそのまま書かれる
  （見たとおりに書く）。守るのは**見えていない範囲**、つまりブロックの外だけでよい。
- **なぜ同期をフォームの 2 キーに限るのか。** 画面の中の双方向同期は、両方向の変換が 1 対 1 でないと値が化ける。
  `model` / `model_class` は単純なスカラーなので 1 対 1 に書ける。`brief`（複数行）や `on_fail`（入れ子）を欄にすると
  そうはいかない。フォームに無いキーは yml の欄だけで直す、という線にしておく。

## 結果（トレードオフ）

- 運転員は工程詳細から `timeout_min` / `next` / `on_pass` / `on_fail` / `inputs` / `outputs` / `brief` も変えられる。
  片方の欄を直すと、もう片方の欄にもその場で出る（保存はしていない）。
- **`brief` を画面から変えられるようになった。** agent への指示文そのものなので、モデルを替えるより結果が大きく動く。
  下見に前後は出るが、その変更が run の結果にどう効くかは機械では分からない。
- ブロックの中を壊しても、壊れるのはその工程のブロックだけ（schema で落ちるので保存もされない）。
  ただし**読めるが意図と違う**入力（`timeout_min: 1` など）は schema を通るので、そのまま保存される。
- 変更記録（`logs/config-changes.jsonl`）に `key: "block"` の行が増える。`before` / `after` は変わったキーの要約で、
  ブロックの原文は残らない。原文に戻すには退避した控え（`.bak-<時刻>`）を使う。
- `id` と担い手の種類を変えたい運転員は、今までどおり制御系で yml を直すことになる（この画面の外に出る）。
  そのときに変更前後の実効値・影響する工程が見えないのは、ADR-0065 から変わっていない。
