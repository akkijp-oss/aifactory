# ADR 0077: 票の先行条件は人が書く 1 列（`depends_on`）にする。PM はそれだけを読み、本文の自由文は解釈しない

- 状態: Accepted
- 日付: 2026-09-15
- supersedes: ADR-0074 決定 5（`reason_code` の語彙に `blocked_by_dependency` を 1 語足す。他の決定はそのまま）

## 状況

2026-09-15、ADR-0074 の `pm_tick`（#537）を ctl へ配備し、**提案モードのまま本物の板に当てた**。その第 1 号の提案が
「**#538 を今すぐ起動せよ**」だった。

```
state = idle
board = {"readable": true, "reason": "ok", "counts": {"todo": 16, "blocked": 13, ...}}
next  = {"reason": "picked_next", "ticket": {"id": 538, ...}, "launchable": true}
```

ところが **#538 の本文自身**が「先行票（#534/#535/#536/#537）の着地後、かつ #537 の propose の提案が妥当だと
確認できてから起動する」と定めている。つまり **止めてある票を指して「起動可能」と言った**。

原因は 1 つだけである。`pm_decide` は `kb next`（`status='todo'` を `id` 順に 1 件）で選んでいるだけで、
**票本文が宣言した先行条件を読んでいない**。`blocked` の 13 件は正しく除外できており、状態の導出
（`idle` / `board.readable` / `runs.readable`）も正しく働いていた。**欠けていたのは依存関係の概念だけ**である。

この検証で VM も鍵も焼いていない。`propose` を先に入れた設計（ADR-0074 決定 3）が、まさにこの用途で効いた
——`auto` から作っていたら、5 分後の tick が止めてある票を起動していた。

## 決定

1. **先行条件は票メタの 1 列 `depends_on`（票番号をカンマ区切りで並べた `TEXT`）に持たせ、人が書く。**
   `kanban.db` の `tickets` に列を 1 つ足す。正規化した別テーブルは作らない（既存の列はすべて単純列で、
   依存は「並び」以上の構造を今のところ必要としない）。

2. **本文の自由文を機械が解釈しない。** 「先行票」「〜の着地後」といった文面から依存を推測すると、
   誤検知（本文が例示として他票に触れただけ）と取りこぼし（言い回しが表に無い）の**両方**が出る。
   これは #552 と同じ理由による同じ判断である。人が `kb set 538 --depends 534,535,536,537` と書く。

3. **判定は `core.py` に置き、`kb next` は薄いままにする。** ADR-0074 決定 1（判定の正本は core、`kb` は
   状態を変える薄い CLI。ADR-0015 を継承）をそのまま適用する。`pm_status()` が `kb next` の 1 件を受け取った
   直後に先行条件を確かめ、未完了の先行票を持つ票を飛ばして次の todo を見る。同じ判定を 2 か所に持たない。

4. **`reason_code` / `next.reason` の語彙に `blocked_by_dependency` を 1 語足す**（ADR-0074 決定 5 の表を継承）。
   `no_todo`（候補が 0 件）とも `board_unreadable`（板を読めていない）とも**別の値**にする。
   ★依存で選べないのは**確かめた結論**であって、**読めていない**のとは別である（#535 / #536 / #537 と同じ型）。
   `state` は `idle` のまま——板は読めているので、人間待ち（`blocked`）へ格上げしない。

5. **書けていない・確かめられないものは「未完了」に倒す。** `depends_on` に書いた id が DB に無いとき
   （まだ起票していない票・他 PJ の票）は、`status = null` の未完了として扱い、その票を飛ばす。
   `kb` 側で存在検査をしない代わりに、読む側が安全側へ倒す。

6. **`depends_on` を持たない票の挙動は変えない。** `NULL` / 空文字列 / 列そのものが無い古い行の 3 つを
   すべて「依存なし」として同じに扱う。運用中の `kanban.db` には列が無いので、`kb` が起動のたびに
   冪等な `ALTER TABLE ... ADD COLUMN` で補う（`CREATE TABLE IF NOT EXISTS` は既存表を変えないため）。

7. **飛ばした票と、その未完了の先行票を `facts.skipped_by_dependency` に残す。**
   画面の主役は理由なので、「なぜ他を選ばなかったか」を機械で読める形で置く（日本語の説明文は書かない）。

## 理由

**依存は「誰が書くか」が設計の本体である。** 本文の日本語はもともと人間の合意のために書かれていて、
機械の入力として設計されていない。そこから推測を始めると、外したときに「なぜ PM がその票を選んだ／
選ばなかったのか」を誰も再現できなくなる。1 列にすれば、書いた事実が `kb history` に残り、間違いも
`kb set --depends ''` で消せる。

**語彙を分けるのは、今回まさにそれで事故ったからである。** `next.reason` が `picked_next` だったから
「起動可能」と読めた。ここに「依存で選べない」を `no_todo` として混ぜると、今度は「候補が尽きた」と
「順番を待っている」の区別が付かなくなり、板を 16 件抱えたまま `no_todo` と言う口ができあがる。

## 結果

- 止めてある票を PM が「今すぐ起動せよ」と提案しなくなる。#538（auto モード）の前提が満たされる。
- 依存は 1 段だけ見る（先行票そのものの先行票までは辿らない）。実データで足りるかを見てから決める、という
  意味で意図的に浅い。**循環依存の検出もしない**（1 段しか見ないので無限には回らない）。必要になったら別票。
- トレードオフ:
  - `kb next` は依存を見ないままなので、`bin/dispatch`（`kb next` → `kb run`）は**依存を見ない**。
    人が直に配車すれば止めてある票も回る。判定を 2 か所に持たない（決定 3）方を優先した結果で、
    dispatch 側にも効かせるなら別票で `core` の判定を通す形にする。
  - 先行票を書き忘れた票は今までどおり選ばれる。この仕組みは「宣言したものを守る」だけで、
    宣言していない依存は見つけない。
  - `depends_on` に他 PJ の票を書くと、その PJ を絞った `pm_status` からは status を引けるが、
    票が消えていれば `null` = 未完了のままになり、その票は永久に選ばれない。`facts` に残るので画面から追える。
  - 候補が全部依存で止まっているとき、`next.ticket` は `null` になる（`no_todo` と同じ形）。飛ばした票を
    画面の主役に出したくなったら別票——材料は `facts.skipped_by_dependency` に残してある。
