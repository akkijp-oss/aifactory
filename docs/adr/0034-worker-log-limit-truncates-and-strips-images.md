# ADR 0034: ワーカーのログ上限は切り捨てで扱う。画像の base64 は記録前に置き換える

- 状態: Accepted
- 日付: 2026-09-09

## 状況

`computer_use: true` の run で、agent 工程の `guest-exec` が 1 操作 16 MiB のログ上限に当たり、結果が `uncertain` になって Mac worker が lease ごと塞がる事故が起きた（2026-09-09、run `2026-09-09-asura-270`）。

原因は 2 つが重なっている。

1. **画像がログに載る。** ゲスト内の `claude -p --output-format stream-json` は、screenshot の `tool_result` を `{"type":"image","source":{"type":"base64",...,"data":"..."}}` として 1 行に出す。1 枚およそ 1 MB なので、GUI をまともに確認すると 16 枚前後で上限に達する。実測のログは 16,740,144 bytes だった。
2. **上限が失敗として扱われる。** `logWriter.Write` が上限で error を返す設計だった。`os/exec` のコピー goroutine はそこで止まり、`tart exec` の stdout パイプが閉じて `tart exec` が切れる。さらに `execute` の defer にある `flush()` が同じ error を返し、exit code が取れていても結果を無条件に `uncertain` へ上書きしていた。

このとき**ゲストは止まっていない**。worker は `stopGuest` を通らない経路で終わっており、ゲスト内の `timeout 60m claude -p` は stdout の書き先を失ったまま走り続け、コミットと成果物を作り続けていた。それでも制御系は `uncertain` を見て worker を予約したままにするので、管理者が `resolve --confirmed-stopped` するまで次の run が動かない。

上限そのものは制御系（`workers/lib/pull.py` の `MAX_LOG`）とも揃っている値で、記録の総容量に自動管理が無い以上は残したい。

## 決定

1. **ログ上限は失敗ではなく切り捨てとして扱う。** `logWriter.Write` は上限に達しても error を返さず、入力長を返して以降の出力を捨てる。パイプは閉じないので、ゲストのコマンドは最後まで走り、結果は exit code で `succeeded` / `failed` が決まる。error を返すのは journal を書けなかったときだけで、それは従来どおり `uncertain` にする。
2. **切り捨てた事実を残す。** 捨て始めた位置に `[operation log truncated at 16 MiB; later output was discarded]` の 1 行を 1 回だけ記録し、結果に `truncated: true` を載せる。制御系はこのキーを任意で受け付ける（無ければ従来どおり）。
3. **画像の base64 は記録の前に置き換える。** `"type":"base64"` を含む行の、1000 文字以上続く `"data":"..."` を `"data":"[image N bytes]"` に置き換える。N は復号後のバイト数。行は JSON として妥当なまま保つ。
4. **ログは行単位で組み立てる。** 置換を stream-json の 1 行に対して行うため、`\n` までを 1 単位にまとめてから、従来どおり 16 KiB・文字境界で区切って記録する。改行の来ない出力のために 8 MiB の安全弁を置く。
5. **上限値 16 MiB は変えない。** 制御系との整合を崩さない。

## 理由

- **なぜ切り捨てで、上限の引き上げではないのか。** 上限を上げても画像が載る限りいつか当たる。当たったときに worker が塞がることこそが事故で、そこを直せば上限の値は運用で決められる。総容量の自動管理が無い以上、上限を外す判断は別に立てる。
- **なぜ画像を捨ててよいのか。** 画像はゲスト側のファイルとして残っており（`screenshot-latest.png` 等）、成果物回収で取れる。ログに必要なのは「何バイトの画像が返った」までで、base64 そのものではない。
- **なぜ置換を「画像」と限定しないのか。** `"type":"base64"` を目印にしつつ、判定は `data` の長さで行う。厳密に画像だけを選ぶには stream-json の構造を worker が解釈することになり、ゲスト側の出力形式に worker を結び付けてしまう。誤って置換しても失われるのはゲストに残っている中身だけで、安全側に倒れている。
- **なぜ 1000 文字なのか。** Go の `regexp` が受け付ける繰り返し回数の上限が 1000 で、それでも復号後 750 バイト。通常の `data` フィールドがこの長さになることはない。
- **なぜゲストを止めないのか。** 上限に達しただけでゲストを止めると、ログが多い run ほど成果物を失う。切り捨てならコマンドは完走し、結果も成果物も残る。ログ上限がゲストの生死に関わらなくなるので、「ゲストは止まらない」という以前の注意書き自体が不要になる。

## 結果（トレードオフ）

- 上限を超えた run では、失敗の原因が捨てられた側に入っていることがある。切り捨て行が入るので「見えていない部分がある」ことは分かる。上限の引き上げは別チケットに残す。
- 改行を出さない長い出力（プログレス表示など）は、8 MiB の安全弁に達するまでコンソールの追い読みに出てこない。行の来る通常の出力では従来と変わらない。
- 画像以外でも 1000 文字以上の base64 な `data` は置き換わる。
- 新しい worker が `truncated` を送るので、**制御系を先に、または同時に更新する**必要がある。切り捨てが起きない限りキーは出ない（`omitempty`）ので、それまでは互換。
