# ADR 0055: チケット詳細は「読む → 状況 → 操作 → 記録」の順に DOM を並べ、操作領域の強いボタンは 1 つにする

- 状態: Accepted
- 日付: 2026-09-07

## 状況

チケット詳細（`console/static/app.js` の `viewTicket()`）は、見出しとメモの次に `grid2` の 2 カラムを置き、
左に「runner で回す」「状態を進める」「項目を直す」「実行記録」「このコンソールのジョブ」、右に「本文」「添付」「履歴」を並べていた。

- 広い画面では、先に読む側（左）が操作フォーム群で、依頼の中身（本文）は右にある。
- `grid2` は幅 1100px 以下で 1 カラムになる（`style.css`）。そこでは **DOM 順がそのまま表示順**になり、操作群が全部本文より前に出る。
- 読み上げ（スクリーンリーダー）と Tab 順も DOM 順なので、狭幅と同じく操作群が本文に先行する。

内容を確認したいだけの利用者が、workflow の選び直し・VM を返却しない（`--keep`）・`--resume`・「開始にする」といった
判断項目を通過してからでないと依頼本文に届かない。加えて、

- 完了ずみのチケットでは、実行の塊に出す「未着手に戻す（やり直す）」と、状態の塊の `done` の遷移が同じ操作を 2 個描いていた。
- 未着手では「実行する」（runner を回す）と「開始にする」（状態だけ変える）が両方とも強いボタン（`primary`）で、効果の違いが色から読めなかった。

完了条件は独立フィールドではなく、本文 Markdown 末尾の `## 完了条件` 節として書く運用（`kanban/README.md`）。

## 決定

1. **読む順を DOM で決める。** CSS の `order` では狭幅と読み上げの順が直らないので、`viewTicket()` のテンプレートそのものを並べ替える。
   順は 見出し → メモ → 実行状況（動いているときだけ 1 行） → **本文 → 添付** → 操作 → 実行記録 → ジョブ → 履歴。
2. **2 カラム（`grid2`）は畳まず、左右の中身を入れ替える。** 左（先に読む側）に本文と添付、右に操作・記録を置く。
   広い画面では本文が左に来て、狭い画面と読み上げでは DOM 順どおり本文が先に来る。ブレークポイントは変えない。
3. **完了条件は本文の中のままにする。** `## 完了条件` 節を切り出して別枠に先出しする解析は入れない。本文パネルが先に来れば完了条件も操作より先に読める。
4. **実行・状態を進める・項目を直すを 1 枚の「操作」パネルにまとめ、`<h3>` で 3 つの塊に分ける。** CLI 名は今までどおり見出しの脇に等幅の小文字で添える。
5. **操作領域の強いボタンは 1 つだけにする。** `primary` は「実行する」（実行できないときは、隣に置く次の一手「未着手に戻す（やり直す）」）に限り、
   状態を進めるボタンからは外す。状態の塊には「runner は動かしません。記録の状態だけを変えます。」を添え、効果の違いを文でも言う。
6. **同じ操作を 2 か所に描かない。** 完了ずみのときの `reopen` は実行の塊の次の一手として出す約束（`console/UX.md`）を正本にし、状態の塊からは落とす。
   状態の塊が空になったら、そのことと上のボタンを指す 1 文（`T.help.moveNone`）を出す。
7. **実行の詳細設定は畳む。** workflow の選び直し・`--keep`・`--resume`・dry-run を素の `<details>` に入れる。
   「実行する」と状態別の案内（`T.help.run*`）は畳まない。`render()` は件数が同じなら `details` の開閉を保つので、5 秒更新で閉じない。
8. **実行状況の 1 行は既存の判定を使う。** 最新の run（`d.runs[0]`）が `running` のときだけ、ボードのカード（ADR-0054）と同じく
   `current.step` があれば工程と経過時間、無ければ `次は <工程>` を出し、実行記録へのリンクを添える。API は変えない。

## 理由

- **なぜ CSS ではなく DOM を並べ替えるのか。** 完了条件が「読み上げでも狭い画面でも本文が先」なので、視覚順だけを変える `order` では満たせない。
  1 カラム化するレイアウトでは DOM 順が唯一の正本になる。
- **なぜ 2 カラムを畳まないのか。** 本文を全幅にすると広い画面で 1 行が長くなり、読みやすさが落ちる。左右の入れ替えだけで
  「広い画面では先に読む側」「狭い画面では先に来る」の両方が同時に満たせるので、レイアウトの作り替えまで踏み込まない。
- **なぜ完了条件を切り出さないのか。** 切り出しは本文 Markdown の見出しに依存する新しい解析で、書き方の揺れ（`## 完了条件` の表記、節の位置）で
  静かに空になる。本文が先に来れば読む順の要件は満たせるので、壊れやすい仕掛けを増やさない。Markdown の見せ方の改善は別の判断として扱う。
- **なぜ強いボタンを 1 つに絞るのか。** ADR-0019 の「摩擦は危険性に比例させる」を色にも当てる。VM を 1 台借りて 60 分回す「実行する」と、
  台帳の 1 行を書き換えるだけの「開始にする」が同じ見え方なら、色は危険度の情報を持たない。
- **なぜ操作を 1 枚のパネルにまとめるのか。** 3 枚に分かれていると「どこからが手を動かす領域か」の境目が無く、読むだけの利用者が
  どこで読み終えてよいか分からない。1 枚にまとめて `<h2>` を 1 つにすれば、読み上げの見出し送りでも操作領域を丸ごと飛ばせる。
- **なぜ `<details>` なのか。** 素の HTML なので Tab で届き Enter で開く。新しい JS も ARIA の手当ても要らない（`console` は標準機能で作る方針）。

## 結果（トレードオフ）

- 広い画面では、これまで左上にあった「実行する」が右上へ移る。毎日押す運転員には位置替えのコストが 1 回かかる。
- 実行の詳細設定（workflow の選び直し・`--keep`・`--resume`・dry-run）は既定で畳まれるので、毎回 dry-run から始める使い方では 1 クリック増える。
  折りたたみの中の要素は DOM には残るので、実行の処理と既存のテストはそのまま動く。
- 完了ずみのチケットでは、状態の塊にボタンが 1 つも出なくなる。空の塊を見せる代わりに、上のボタンを名指しする 1 文を出す。
- 実行状況の 1 行は最新の run が `running` のときだけ出る。`not_started` や `abandoned` の run では出ないので、そこは今までどおり実行記録のパネルで読む。
- `.panel h3` を新しく足したので、他の画面のパネルで `<h3>` を使うとこの見た目に揃う。
