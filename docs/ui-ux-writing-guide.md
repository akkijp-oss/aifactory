# SaaS UI/UX 設計・UXライティング ノウハウ

SaaSのUIを「機能の一覧」ではなく「ユーザーの一つ一つの操作」から設計するための考え方と、アプリ内の日本語文言を高い品質で維持するための実務ノウハウをまとめたものです。

---

## 第1部 UI/UX設計の原則 — 操作を4つの軸で観察する

UIを設計するときは、機能を並べるのではなく、ユーザーの一つ一つの操作を **文脈・頻度・危険性・次の行動** の4つの軸で観察して配置する。

### 1. その機能は「どう使われるか」 — 文脈と目的

まず問うべきは「ユーザーはこの画面に何をしに来たか」である。同じ「検索」でも、毎朝必ず開くダッシュボードの検索と、月に一度の請求書探しの検索は別物である。

実務では、ユーザーの目的を「ジョブ」(Jobs To Be Done) として書き出し、機能ごとに次を1行で定義する。

> 誰が・いつ・何のトリガーで・何を達成したくて使うか

これが書けない機能は、要件が曖昧か、そもそも不要な機能であることが多い。

**原則**

- 機能名ではなくユーザーの動詞で設計する(「エクスポート機能」ではなく「経理に月次データを渡す」)。
- UIの言葉をユーザーの語彙に合わせる(Nielsen「システムと実世界の一致」)。

### 2. 使用頻度 — 頻度が「場所」と「深さ」を決める

頻度は情報設計の最重要変数である。

| 頻度 | 配置 |
|---|---|
| 毎日・1日に何度も | メインナビゲーション、ファーストビューに常駐。キーボードショートカットも用意 |
| 週に数回 | ワンクリック以内で到達できる位置 |
| 月に一度・初回設定のみ | 「設定」やメニューの奥に格納し、検索・ヘルプで補う |
| ほぼ使わないが重要(削除・解約など) | 意図的に到達コストを高くしてよい |

**根拠となる法則**

- Fittsの法則: よく使うものは大きく、近くに。
- Hickの法則: 選択肢が増えるほど判断が遅くなる。低頻度の項目は表から消す。
- プログレッシブ・ディスクロージャー: 必要なときにだけ詳細を見せる。

**よくある失敗**: 開発側にとって「重要」な機能を、使用頻度を無視して目立つ場所に置く。頻度は推測せず、イベントログやヒートマップで測ってから配置を決める。

### 3. 操作の危険性 — 「取り返しがつくか」で摩擦の量を設計する

操作は次の3段階に分けられる。

| 分類 | 例 | 設計 |
|---|---|---|
| 可逆・影響小 | フィルター変更、並び替え | 確認ダイアログは一切出さない |
| 可逆・影響広 | 一括編集、設定変更 | 「実行してから取り消せる」設計を優先(Undo、トーストの「元に戻す」、ゴミ箱、下書き保存) |
| 不可逆・影響大 | 削除、送信、決済、他者への通知 | 複数の防護策を組み合わせる(下記) |

**原則: 危険性に比例して摩擦を入れる。**

確認ダイアログを乱発すると、ユーザーは読まずにOKを押す癖がつき、本当に危険な場面で効かなくなる。確認ダイアログより「取り消し可能性」のほうが、体験もエラー率も良いというのはHCI研究の一貫した知見である。

**不可逆・影響大の操作に対する防護策**

- ボタンの色と位置を通常操作と明確に分ける(危険色、通常ボタンから離した位置)。
- 削除対象の名前を入力させる。
- 影響範囲を数字で見せる(「このプロジェクトと配下の42件のタスクが削除されます」)。
- 権限で実行者を絞る。

**配置上の原則**

- 危険なボタンを頻繁に使うボタンの隣に置かない(誤タップ防止)。
- 破壊的操作のデフォルトフォーカスは「キャンセル」側にする。

### 4. 次に何をしてほしいか — 操作の「後」を設計する

多くのUIは操作の「前」ばかり設計して、操作が完了した瞬間に何が起きるかを放置している。ユーザーが最も迷うのは操作直後である。

**原則: 状態を必ず可視化し、自然な次の一手を一つだけ提示する。**

- 保存後: 「保存しました」の明示と、次に開くべき画面への導線。
- 作成後: 空の状態(Empty State)を放置せず「最初のメンバーを招待する」など、次の行動をそのまま示す。
- 完了画面: 次にやることが複数あっても、主要な一つをプライマリボタンにし、残りはセカンダリに落とす。
- エラー時: 何が悪かったかではなく「どうすれば直るか」を書く。
- 反映箇所の明示: 操作の結果がどこに反映されたかを、探さなくても分かるようにする(ハイライト、スクロール、リスト先頭への配置)。

これはNielsen「システム状態の可視性」と、フロー全体を一本の道として設計する「ユーザーフロー」の考え方に基づく。オンボーディングやチェックリストは、この「次の一手」を新規ユーザー向けに束ねたものである。

### 実務での進め方 — 4軸の表を作る

機能ごとに次の表を埋める。

| 機能名 | ユーザーの目的(ジョブ) | 使用頻度(日/週/月/初回のみ) | 可逆性と影響範囲 | 操作後の理想的な次の行動 |
|---|---|---|---|---|
| | | | | |

この表を埋めると、ナビゲーションの階層、ボタンの階層(プライマリ・セカンダリ・デンジャー)、確認やUndoの要否、空状態と完了画面の内容が、ほぼ機械的に決まる。

**一貫性**: 同じ危険度の操作は必ず同じ見え方をし、同じ頻度の操作は同じ階層にある。ユーザーは個々の画面を覚えるのではなく「このプロダクトではこう見えるものはこう振る舞う」というルールを学習する。

**参考文献**

- Nielsen Norman Group「10 Usability Heuristics」
- Don Norman『誰のためのデザイン?』(アフォーダンス・フィードバック・エラーの許容)
- Steve Krug『Don't Make Me Think』

## 第2部 UXライティング — アプリ内の日本語文言のノウハウ

一般的なUXライティングの原則に加えて、日本語特有の落とし穴(敬語の重さ、主語の省略、漢語と和語の使い分けなど)がある。

### 文言を書くときの6原則

#### 原則1: ユーザーの行動を書く、システムの動作を書かない

「保存します」はシステムが主語で、ユーザーは押した後に何が起きるかを想像しなければならない。ボタンには「保存」「保存する」のようにユーザーの行為をそのまま書き、ラベルを読めば結果が分かる状態にする。

- 「OK」「はい」「実行」のような中身のないボタンは避け、「削除する」「送信する」と動詞で書く。
- 確認ダイアログでは、ボタンだけ見ても誤操作しない形にする。

| NG | OK |
|---|---|
| 本当に削除しますか? → [はい] [いいえ] | このプロジェクトを削除しますか? → [削除する] [キャンセル] |

#### 原則2: 一文一情報

日本語は接続助詞で文をどこまでも延ばせる。説明文はユーザーが「読む」のではなく「スキャンする」前提で、先頭に結論を置き、短く切る。

| NG | OK |
|---|---|
| 入力内容を確認し、問題がなければ送信ボタンを押して、完了メールをお待ちください | 入力内容を確認してください。送信すると完了メールが届きます。 |

#### 原則3: 敬語は「ですます」で一定にし、過剰な丁寧さを削る

「〜させていただきます」「〜してくださいますようお願い申し上げます」はUIでは冗長で、読み飛ばされる原因になる。「〜してください」で十分丁寧。

- 「〜いたします」「〜致します」など、二重敬語や表記揺れの温床になる表現は最初から使わないと決める。

#### 原則4: エラーは「何が起きたか」より「どうすればいいか」

「エラーが発生しました」「不正な値です」は情報量がゼロ。原因と次の行動を1文ずつ書く。

| NG | OK |
|---|---|
| 不正な値です | メールアドレスの形式が正しくありません。@以降を確認してください |

- ユーザーを責める言葉(「不正」「無効」「失敗しました」)は中立な言い方に置き換える。

#### 原則5: システムの都合の言葉を出さない

「セッションがタイムアウトしました」「バリデーションエラー」「レコード」「フェッチ」は開発者の語彙。ユーザーの体験として書き直す。

| NG | OK |
|---|---|
| セッションがタイムアウトしました | 一定時間操作がなかったため、ログアウトしました。もう一度ログインしてください |

#### 原則6: 空状態と成功時にこそ文章を使う

- 空状態: 「データがありません」ではなく「最初の顧客を登録すると、ここに一覧が表示されます」と、次の行動を促す。
- 成功時: トーストは「保存しました」だけで良い。余計な感謝や装飾は不要。

### 日本語特有の注意点

**主語・目的語の省略**
「送信しました」は自分が送ったのか相手から届いたのか曖昧になる。「招待メールを送信しました」と目的語を残して補う。

**漢語と和語の使い分け**

- 漢語(「登録」「削除」「更新」)は短く、見出しやボタンに向く。
- 和語(「取り消す」「やり直す」「もどす」)は柔らかく、説明文に向く。
- 混在させると印象がばらつくので、「ボタンは漢語+する、説明は和語寄り」など場所ごとにルールを決める。

**カタカナ語**
ユーザー層が理解できるかで判断する。BtoBのIT系ユーザーなら「アーカイブ」「エクスポート」は通じるが、一般業務のユーザーなら「保管」「書き出し」のほうが安全。迷ったら実際のユーザー5人ほどに聞く。

**表記揺れ**
日本語UIで最も頻発する品質問題。どちらかに統一する。

| 揺れの例 | 推奨 |
|---|---|
| お客様 / お客さま | どちらかに統一 |
| できる / 出来る | できる |
| 下さい / ください | ください(補助動詞はひらがな) |
| 頂く / いただく | いただく(補助動詞はひらがな。「頂く=もらう」の実質動詞は漢字) |
| サーバ / サーバー | どちらかに統一 |

補助動詞はひらがな、実質動詞は漢字、という新聞ルールが一般的な基準。

**長音・半角全角・記号**
英数字は半角、記号(括弧、コロン、感嘆符)の全角/半角、数字の桁区切りの有無などを決める。揃っていないと「雑な製品」という印象を与える。

### チームで再現するための仕組み

個人のセンスに任せると必ず崩れる。以下を仕組み化する。

#### 1. ボイス&トーンガイド(1ページ)

- 人格の定義: 「このプロダクトは、有能で落ち着いた同僚のように話す」
- 禁止事項: 「感嘆符は使わない」「絵文字は使わない」など
- 表記ルール(上記)
- NG/OK対訳表 10〜20個(例: 「〜させていただきます → 〜します」)

長い文書は誰も読まないので、**1ページに収める**ことが最重要。

#### 2. 用語集(ターミノロジー)

プロダクト内の概念(「プロジェクト」「ワークスペース」「メンバー」など)は、UI・ヘルプ・営業資料で必ず同じ言葉で呼ぶ。一つの概念に複数の名前がある状態は、ユーザーが最も混乱する原因。

- 開発のデータモデルや変数名とも対応させると、エンジニアとの認識ずれが減る。

#### 3. 文言の一元管理

文言はコードに直書きせず、文字列リソースとして一箇所に集める(i18nの仕組みをそのまま使えばよく、日本語だけでも価値がある)。

- 全文言が一覧できると、表記揺れのチェック、トーンの見直し、後からの一括修正が現実的になる。
- textlintなどの校正ツールをリソースファイルに対してCIで走らせ、「下さい」「出来る」「二重敬語」などを機械的に弾く。

#### 4. レビューの2つの問い

文言をデザインレビューの項目に入れ、毎回次の2問を問う。

1. このボタンのラベルだけを見て、押すと何が起きるか説明できるか?
2. このエラーを読んで、次に何をすればいいか分かるか?

可能なら、UIの文脈を切り離してボタンラベルだけを並べたものを他人に見せ、意味が推測できるか試す。

#### 5. 文言は実物で読む

Figmaや仕様書上で綺麗でも、モバイルの幅で改行された瞬間に意味が変わったり、動的に入る値(ユーザー名、件数)で助詞が破綻したりする。

- 日本語は数による語形変化がないため英語より楽だが、名前が長い場合の省略や、ゼロ件のときの表現は個別に確認する。

## 付録: すぐ使えるチェックリスト

**機能・画面を設計するとき**

- [ ] この機能のジョブ(誰が・いつ・何のために)を1行で書けるか
- [ ] 使用頻度に応じた階層に置いているか
- [ ] 危険度に応じた摩擦(Undo / 確認 / 名前入力)になっているか
- [ ] 危険なボタンが頻用ボタンの隣にないか
- [ ] 操作直後の状態表示と「次の一手」が設計されているか
- [ ] 空状態に次の行動が示されているか

**文言を書くとき**

- [ ] ボタンはユーザーの行為を動詞で書いているか(「OK」「はい」を使っていないか)
- [ ] 一文一情報になっているか
- [ ] 過剰な敬語・二重敬語を使っていないか
- [ ] エラー文に「どうすればいいか」が書かれているか
- [ ] 開発者の語彙(セッション、バリデーション等)が出ていないか
- [ ] 主語・目的語の省略で誤読が起きないか
- [ ] 用語集・表記ルールに従っているか
- [ ] 実際の画面幅・実データで確認したか
