### Fixed
- **A step killed by its time limit no longer throws away the uncommitted work, and says "timeout" instead of showing the last thing the agent printed.** `timeout <timeout_min>m claude …` cuts an agent step at 60 minutes by default, and the runner treated the resulting exit code 124 as any other failure: it returned before saving the agent's changes, so `sandbox release` took the working tree with it and the preserve branch came out identical to base — one implement step lost 14 files' worth of work and about 75 minutes of VM time. The runner now handles 124 on its own: it commits the uncommitted **tracked** changes as `wip: step timeout` (never `git add -A`, so generated files and local databases stay out) before failing the step, which puts the half-finished implementation on `origin/sandbox/<id>-<wf>-wip` for the next run to continue from. `state.json`'s `error` is now the single line `implement: 時間上限 60 分で中断（timeout）`; the tail of the agent's standard output moved to a separate `last_output` field, so the reason is no longer the agent's last line of output (a lint summary such as `✖ 1317 problems (0 errors, 1317 warnings)` used to read as "lint failed" when lint had in fact passed). The step's `history` entry carries `failure: "timeout"` and `timeout_min`, which the web console's run view and the MCP `run_show` turn into "this step was cut off at its time limit; the committed part is on the wip branch". The prompt for every step that commits now states its limit in minutes and asks for a `wip:` commit every 30 minutes, and the implementer's constitution says the same for all workflows. Default limits are unchanged and are listed per workflow in `workflow/README.md`
