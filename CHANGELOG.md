# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- Console run page: an *Outcome* panel now leads the page (ADR-0025). It says in one sentence what happened — a PR was created, the step it stopped at, how many times a gate failed before it went to a human, or that the record does not say — lists the failing gates read out of `work/gates.txt`, and puts *Read the reason* (opens that very file), *Read the report* and *Open the ticket* next to it, followed by the ticket's current state and a link to a newer run when the ticket has one. The file list is no longer one flat `rglob`: artifacts come first, named from the workflow's `outputs` (report, plan, gate results, ticket) rather than hard-coded file names, then the step logs in order, with prompts, `.jsonl`, locks and patches collapsed under *Other files*. The reason file is what opens by default on a finished run. The runner and `state.json` are unchanged; everything is derived from the existing record, and what cannot be derived is shown as unknown
- **Console logs screen: a table you can follow from a log line to the ticket (ADR-0027)**. `#/logs` used to dump `intake.log` and `dispatch.log` into two `<pre>` blocks, so reading it meant knowing the backends' output format — unlabelled numbers like `0.9` from intake, `rc=2 status=todo` and `→ blocked` from dispatch — and the ticket numbers in it were plain text with nowhere to go. Both logs are now derived into one table, newest first, with named columns: time, action (filed / started / finished / moved to a human / skipped / no todo), project, ticket, result (the kind and confidence for intake, the state badge for dispatch) and reason (the intake reason with the model beside it, the exit code and duration for a finished run, why a ticket was skipped). The ticket number is an ordinary link to that ticket and the rest of the row is clickable. The table narrows by ticket number (prefix match), project and kind (intake / dispatch), all ANDed, with the filter in the URL query (`#/logs?q=&pj=&src=`) so the browser's back button restores it, and it states "{n} of {m}" above the table. Lines that match no rule are not hidden: they appear as *other* with their original text, and the untouched raw logs stay under *Show the raw log*. `glue/bin/intake` and `glue/bin/dispatch` are unchanged — `GET /api/logs` keeps its `intake` / `dispatch` text (so the MCP `logs` tool is unaffected) and adds the derived `entries` and `total`
- **Console: a *tickets* screen (`#/tickets`)**. Completed tickets past the board's newest 15 used to be reachable only by leaving the browser for `kb list --all`. The done column still caps at 15 so the board stays readable, but its overflow line is now a link (*See all n more*) into the new screen, and the board header carries *Search the list*. The screen lists every ticket newest first and narrows them by number (prefix match), title (case-insensitive substring), project and state, all ANDed; it states "{n} of {m}" above the table and, when nothing matches, says which condition to relax. The filters live in the URL query (`#/tickets?q=&pj=&status=`, rewritten with `history.replaceState` as you type, so the text field keeps focus), so opening a ticket and pressing the browser's back button restores the same filtered list, and the ticket's breadcrumb leads back to it. Filtering happens in the browser over the tickets `GET /api/tickets` already returns, so there is no API change

- **Console intake: the screen says what filing does, not which CLI it calls**. The two panels were headed *File from free text* / *File from a well-formed body* with a subtitle naming the backends (`intake` with one LLM call, `kb new`) and a note about calling `claude -p` on the Mac, so nothing on screen said whether filing also started a run, or which panel to pick. They now read *File from prose* and *Write the title and criteria yourself*, the subtitle describes what each side does with your text, and the page ends with 起票しただけでは実行は始まりません — naming a ticket's *Run* and the board's *Dispatch* as the two ways a runner starts. The kind select's inline description no longer comes from the workflow YAML's `description` (a list of steps and role names written for developers): `strings.js` gains a `kind` group saying when to pick each of bug / chore / hotfix / feature / docs / research / merge-pr, with the YAML text kept as the fallback for a kind the console does not know. The body field gets a placeholder skeleton (`## 背景` and a `## 完了条件` checklist) next to the title field's existing example, and the runs and jobs screens describe what their records are instead of where they are stored. `console/tests/test_strings.py` checks that `kind.*` covers every workflow in `workflow/kit/workflows/` and that the body skeleton keeps its completion-criteria checklist; the workflow definitions, the API and `core.py` are unchanged

### Changed
- **`kb run --workflow X` no longer rewrites the ticket's `kind`.** Running a `bug` ticket once through `merge-pr` renamed its kind to `merge-pr` in the ledger and never put it back, even when the run failed — `kb list` then described the work by how it was last executed. The kind is what the work *is* and only `kb set --kind` changes it; how a run was executed is recorded in the history (`workflow → X`) and in `runs/<run>/state.json`. A `--resume` without `--workflow` now restarts from that `state.json`'s workflow instead of the kind (ADR-0029). Ledgers already rewritten are not repaired automatically
- **MCP `ticket_action` with `action: sync` no longer writes by default** (compatibility change). The console's *Sync the state from the run record* has previewed itself since the dialog was added, but the MCP tool called `kb sync` straight away, so an AI session could roll a finished ticket back to whatever an old run recorded. `sync` now defaults to `dry_run: true`: it returns the same before/after the HTTP preview returns (state, note, the run and whether the ticket was updated after that run) and writes nothing. Passing `dry_run: false` writes, and the response still carries the before/after plus `kb`'s output; when the ticket was updated after the run finished, both answers carry a `warning` saying the update is being (or has been) overwritten. `ticket_show` gains `sync_preview` for a ticket that has a run, so the caller sees the consequence before it acts. The console screen is unchanged — its dialog now sends `dry_run: false` after you confirm — and `kanban/bin/kb` is untouched

### Fixed
- **The control plane's `gh` now issues its own token from the GitHub App**, so `merge-pr` (any `start: pr` workflow) runs from MCP and from the console API alike. `workflow/bin/run` calls `gh pr view` on the control plane before it takes a VM; the token for it was expected in `~/.config/aifactory/ctl.env` as a hand-made PAT, but the template ships `GH_TOKEN=` (empty) and `console/bin/mcp`, started over ssh, never read that file at all — both paths ended at `gh auth login` and a traceback. The runner's new `ensure_gh_token()` asks `sandbox gh-app token <pj>` for a one-hour, repository-scoped installation token (ADR-0008) when `GH_TOKEN` is missing or empty, puts it in its own environment (children inherit it) and prints only where it came from, never the value; when neither is available, the single error message carries both the `gh` failure and the reason the App could not issue one. `console/bin/mcp` now reads `ctl.env` on start (`core.load_ctl_env()`, overridable with `AIFACTORY_CTL_ENV`), filling in only variables that are unset, so both entry points run children with the same secrets. `GH_TOKEN` in `ctl.env` becomes the fallback for hosts without the App and may stay empty (ADR-0029)
- Console navigation: the badges next to *Board* and *Runs* count every project, but nothing on screen said so, so picking a project on the board — which does narrow the strip, the columns and the run list — left the badges showing a different, larger number with no explanation. The badges keep counting every project (they sit next to links to other screens, so a project-scoped number there would be misleading), and now say it: both carry a `title` explaining the scope, and the board's scope line reads 集計と列の対象: PJ {pj}（左のナビの数字はすべての PJ） when a project is selected. `console/UX.md` records the decision on the board row
- Console board: with seven or more runs going at once, the selected project's run could vanish from the *in progress* cell. `overview` capped `runs_active` at six and the browser filtered that page of six by project afterwards, so a project whose run was older than six others' simply had nothing to show — and the pool holds three VMs per project, so this happens in practice. `core.overview` now takes `pj` (`GET /api/overview?pj=`, MCP `overview(pj)`) and filters the run lists before applying the cap, returning `runs_active_n` (the count after filtering), the `limit` and the `pj` it used; the board asks for its project's overview and, when more runs are active than fit, ends the cell with a link to the run records. The navigation's run badge counts `runs_active_n` instead of the capped list, and `counts` stays project-wide
- Console: a run whose runner died without writing `finished` no longer sits on the board as "in progress" forever, next to a job the same screen calls failed. `core.run_liveness` matches every seemingly running run against the jobs this console started (`run_hint`, else the same ticket started no earlier than the run) and, when that job has ended and `state.json` has not been written since, reports the run as `abandoned`: the board, the run list and a ticket's run table drop the pulse and label it 中断, `overview` splits it out as `runs_abandoned`, and the run page's *Outcome* panel says the runner ended at that time, that waiting will not help, and which job it was — with *Open the job* as the primary action. A run whose job is still running, or whose `state.json` is newer than the job's end (a `--resume` from the CLI), stays in progress; a run with no job at all is only called abandoned when the ledger already moved that ticket to blocked afterwards. When there is no job and no ledger evidence, nothing changes
- Console run page: a run that failed before its first step (`sandbox take` or the checkout right after it) used to answer "the record does not say why it stopped" even though `state.json` held `result: failed` and the reason. `run_outcome` now reports `failed_before_start` with the last line of `error` as a one-line summary, and the panel leads with it. `run_summary` also fills `pj` and `task` from the run's own name (`<date>-<pj>-<ticket>`) when the record lacks them, so those runs get the ticket link in the header and stay inside the project filter; a `state.json` that cannot be parsed is now reported as 開始前 with `state_error` and the page says the record could not be read instead of calling it a "v0 record", and a missing start time is stated rather than rendered as an empty （ 経過）. Stopped runs also link to the ticket, the job's output and sandbox, and note when the VM is still on loan; *Sync the state from the run record* appears only when the ledger's run is this run and the ticket is still in progress, so a later run or a human's decision is not rolled back
- Console: a run in progress showed an elapsed time that jumped to the right value the moment it finished — the same run read "9 hours 9 minutes" while running and "10 minutes" once done, and its start time differed by 9 hours between the sandbox screen and the job screen. Timestamps were written without a UTC offset (`2026-09-08T00:21:00`) by the runner, `kb` and the console, so the browser read them as its own local time; the gap was exactly the difference between the server's time zone and the browser's, and it disappeared on completion because that view uses the recorded `elapsed_s` in seconds. Records now carry the offset (ADR-0026): `workflow/bin/run`, `kanban/bin/kb` and `console/lib/core.py` write `…+00:00`, and the console fills the offset in when it reads an older record, treating it as the writing host's local time. Every time the API returns — run `started` / `finished` / `current.since` / `history[].at`, ticket `created` / `updated` and history, job `started` / `finished`, file `mtime`, `overview.now`, the sandbox lending time — is offset-aware, so an elapsed time is the same in any browser time zone and no longer jumps at the end. The clock at the bottom of the navigation names the browser's time zone and says when the records are kept in a different one; a missing timestamp now reads 時刻の記録なし instead of an empty cell or a huge duration, and a start time in the future reads 開始が未来の時刻 rather than counting from zero. Comparisons in `after()` no longer fall back to "false" when a record with an offset meets one without
- Console: the run list, the job list and a ticket's job table only reacted to a click anywhere on the row, so the run name and the job's description looked like plain text while the ticket number and the PR next to them were the only real links — keyboard and screen-reader users had no way to reach the detail page. Those names are now ordinary links (`#/run/<name>`, `#/job/<id>`), reachable with Tab, opened with Enter, announced as links and distinguishable from the ticket and PR links by their target; clicking the rest of the row still works. Leaving a list also remembers its scroll position, so the browser's back button returns to the row you came from instead of the top
- Console ticket: the run panel now matches what the ticket can actually do. A done ticket used to show an enabled green *Run* next to a note saying to reopen it first, and `kb run` then refused it; *Run* is now disabled there (with the reason as its title) and *Back to todo (redo)* sits beside it, while dry run stays available. The note under the button is written per state (todo, in progress, review, waiting for a human, done), and the empty run-record text no longer points at a button that is not on screen: it tells you to add `project.yml` when the project has none, to wait when a job is running, and to reopen the ticket when it is done
- Console sandbox: when the ledger holds two leases on the same VM (the same `vmid` under two ticket numbers), the screen used to draw two ordinary rows, say *2 VMs*, count *2 / 3* against the project pool and offer each row its own *Return the VM* with no hint that both point at one machine — returning either one rolls that VM back to `snapshot clean` and destroys the other ticket's work. `GET /api/sandbox` now reports `lease_count`, `vm_count` and `shared` (`{"9213": ["221", "222"]}`), and `GET /api/overview` adds `vms_lent` beside the unchanged `lent`. The heading reads *2 leases, 1 VM*, a warning above the table names the VM and the tickets sharing it, each shared row is badged *shared*, the pool usage counts VMs with the lease count beside it, and the release dialog lists the other tickets, says their work is lost and that their ledger rows stay behind pointing at a rolled-back VM, and requires typing the ticket number even when no run is active. `sandbox ls` prints one row per VM with `TASK` as `221,222` instead of splitting the row across two lines, and the console's pool listing turns that into one link per ticket plus a *shared* badge (a single `#/ticket/221,222` link would not open). `state.json`, `sandbox take` and `sandbox release` are unchanged; the console still only reads the ledger, so an actual duplicate is for a human to resolve
- Sandbox: two `sandbox take` calls started at the same time could hand the same VM to two tasks (both runners then failed on `cannot lock ref` in the same clone). Picking a free VM and reserving it in `state.json` now happens inside a `state.json.lock` critical section (`flock`, falling back to a `state.json.lock.d` mkdir lock where `flock` is missing); the slow part of `take` (rollback, env injection, DNS) stays outside the lock and a failure there drops the reservation instead of leaving a stale entry. `release` writes through the same lock. When the pool is exhausted the later `take` fails with "no free VM" as before
- Console: a finished `kb run` job no longer pushes recovery steps for a ticket that has moved on since. `GET /api/jobs/<id>` now carries the ticket's current state and whether it was updated after the job, so the job's *What to do next* panel turns past tense (primary button *Open the ticket*) once the ticket is done or was edited later, and always shows the job's end time next to the ticket's current state. *Sync the state from the run record* now previews itself first: the new `kb sync --dry-run` (and `GET /api/tickets/<id>/sync-preview`) reports the state and note before and after without writing, the dialog shows both and warns in danger colours when the ticket was updated after that run, and the toast offers *Undo*
- Console board: the pipeline strip counted every project while the columns below it counted only the selected one, so a project filter looked broken. The strip, the "in progress" run list and the columns now all come from the filtered ticket list, the scope is stated above the strip, and the columns follow the strip's order (todo, in progress, review, done, then "waiting for a human" to the side)
- Console intake: typing a request and then stepping over to the logs or settings threw the draft away, with no warning before leaving. All nine fields of both panels (request text, project, kind, dry run, title, body, PR number) are now kept in `sessionStorage` as you type, so a detour, a reload and the browser's back button all bring them back; a *Discard the draft* button (with *Undo* in the toast) is the only way to clear them, and a successful submit clears only that panel
- Runner and kanban: a `kb run` whose `sandbox take` failed used to leave the ticket 実行中 forever with no run, no PR and a `runs/<name>/` holding nothing but `ticket.md`; a re-run only renamed that stub to `-attemptN`. `workflow/bin/run` now writes `state.json` next to `ticket.md` before it takes a VM (`current` = the `take` step), catches any failure in take or in the checkout right after it, records `result: failed`, `next: human` and the reason in `error` (lines that look like credentials are dropped), returns the VM it had already taken and exits 2. `kb run` maps `result: failed` to blocked with that reason in the note, and a runner that exits non-zero without writing `finished` is blocked too instead of staying in progress; `kb sync` is unchanged. The console run page shows the reason under 失敗の理由 and such runs count as finished, not as "not started"
- Console: a run directory that only has `ticket.md` (the runner stopped before writing `state.json`) no longer shows up as "in progress, step 0" with every field empty. `run_summary` now reports `status` (`not_started` / `running` / `finished`), `overview` splits it out as `runs_not_started` and keeps `runs_active` to genuinely running runs, and the board, the run list and the run page label those records 開始前（記録なし）with their name, say which count belongs to tickets and which to run records, and still link to the detail page
- 種別・workflow・役割の一覧から `.` / `_` 始まりのファイル（macOS の `._bug.yml` など）を除いた。起票の種別の初期値を `bug` にし、種別の用途を画面に出す。台帳に workflow の無い種別が入っているときは注意を出す（console / kb / intake）

## [0.3.0] - 2026-09-08

### Added
- **Mac, Windows and Linux workers (ADR-0018, 0020, 0022, 0024)**. Tickets can now run outside the Proxmox sandbox on dedicated hosts that pull work over HTTPS. A Go worker (`workers/cmd/aifactory-worker`) fetches operations from the control plane's queue with a per-worker token and an exclusive per-run lease, streams logs and artifacts back, and needs no inbound connection. macOS: the worker runs on an Apple Silicon host and clones a fresh Tart guest per run. Windows: a service inside a dedicated VM runs tasks as an ordinary user under a Job Object and hands back the workspace. Linux: a systemd service on a dedicated instance runs commands as a dedicated user in transient units. `project.yml` selects them with `backend: macos-pull | windows-pull | linux-pull` and `worker: <id>`; `workers/bin/control` enrolls workers, inspects the journal and resolves stuck operations. Guides: [Mac](docs/macos-worker.md), [Windows](docs/windows-worker.md), [Linux](docs/linux-worker.md)
- **Computer use on those workers (ADR-0023)**. `computer_use: true` in `project.yml` gives every agent in a run a `computer` MCP tool (screenshot, click, move, type including Japanese, keys, scroll) served by `workers/cmd/aifactory-computer` inside the guest; the last screenshot is collected as an artifact. The aifactory MCP server gains `computer_open` / `computer_action` / `computer_close` for driving a worker's screen directly. [Guide](docs/computer-use.md)
- **One-command installers** (`workers/install.sh` for Linux and Mac, `workers/install.ps1` for Windows). They take `AIFACTORY_URL` / `AIFACTORY_WORKER` / `AIFACTORY_TOKEN` from the environment, fetch the source at `AIFACTORY_REF` (default `main`), build with a SHA-256-verified official Go toolchain, install dependencies, the desktop (Xvfb/Openbox on Linux, auto-logon user on Windows when `AIFACTORY_AUTOLOGIN=1`), the services and the computer-use helper, then verify TLS and the token with `POST /v1/check`. Re-running on the same worker is allowed; overwriting a different worker's install or updating during a lease is refused. Verified on all three OSes from the public URL. [Guide](docs/worker-install.md)
- **Console UX pass (ADR-0019)**. Friction now scales with risk: state changes apply immediately with an *Undo* in the toast (`kb set --status <previous>`), real runs and dispatch open an in-page dialog that shows what will happen (dispatch previews the ticket `kb next` will pick, via the new `GET /api/next`), VM release and job stop use a danger-styled dialog that focuses *Cancel* and, when a run is active on that VM, requires typing the ticket number. Finished jobs show a *What to do next* panel (intake → open the created ticket, stopped run → sync the ticket state, release → sandbox). Navigation is ordered by frequency (board / file / runs / jobs / sandbox / logs / settings), dispatch moved from the intake page to a dialog on the board, and `g` + a letter jumps between screens (`?` lists them). An offline banner replaces the bare "disconnected" label
- All UI strings live in `console/static/strings.js`; `console/tests/test_strings.py` (stdlib only, runs in CI) rejects forbidden spellings, non-verb button labels, non-polite sentences, developer vocabulary, glossary drift and any key that is undefined or unused. `console/UX.md` is the one-page voice & tone guide, glossary and per-feature design table; `docs/ui-ux-writing-guide.md` holds the general know-how it applies. Server-side error messages (`core.py`, `bin/console`, `bin/mcp`) now say what happened and what to do
- **Tenants and a control plane on Proxmox (ADR-0017)**. `SB_TENANT` selects an independent environment per organization: its own SDN zone `sb<t>` / vnet `vn<t>` / `/16`, VMID block, names (`sb-<t>-…`), DNS domain `<t>.sb.internal`, firewall groups `sb-<t>`, Proxmox resource pool and user `sb-<t>`. The first environment is the `main` tenant; `07-migrate-naming.sh` moves a pre-rule setup (`sb` / `sbnet` / `aifactory` / `sb.internal`) onto the rule without stopping VMs. `sandbox/proxmox/_tenant.sh` derives all of it; `05-tenant.sh` creates the pool / role / user / ACL; `25-control-lxc.sh` builds a control-plane LXC (`<prefix>-ctl`) holding the checkout, workspace, `sandbox` CLI, web console, documentation site, GitHub App refresh timer and the runner's tools, all under systemd, and issues a pool-scoped Proxmox API token straight into it. Every name carries `sb` and the tenant slug; nothing keeps the old bare names
- `sandbox` CLI: Proxmox **API mode** (`PVE_API_TOKEN` + `PVE_API_URL` + `SB_POOL`) as an alternative to ssh + `qm`; the control plane never holds the host's root. `SB_TENANT` / `SANDBOX_ENV_FILE` pick another tenant's config from the maintainer's machine
- Console: `CONSOLE_TOKEN` passphrase (cookie via `/?token=`, or `Authorization: Bearer`) required to bind anywhere but 127.0.0.1; `/docs/` serves the built documentation site; `console/bin/install.sh --systemd`. `sandbox/bin/install.sh --systemd` installs the token refresh timer on Linux
- Website guide *Per-organization environments (tenants)* (ja / en)
- `.mcp.json` now has `aifactory-local` (was `aifactory`) and `aifactory-ctl`: `console/bin/mcp-remote` runs the MCP server inside the control-plane LXC over ssh (stdio), so AI sessions on a laptop (Claude Code, Codex CLI, any stdio MCP client) work against the Proxmox-hosted workspace. Target via `~/.config/aifactory/mcp-remote.env`
- `sandbox/proxmox/45-pool-keys.sh`: push public keys into existing pool VMs through the guest agent and retake `clean`; `40-pool.sh` now sets cloud-init `sshkeys` on every clone. `run.sh` has `AIFACTORY_LOCAL_TREE=1` to build the control plane from the local working tree

### Changed
- Console: binding to an internal (non-global) address such as `10.77.0.3`, `192.168.x`, or a tailnet `100.64/10` address no longer requires `CONSOLE_TOKEN` (ADR-0021); the tailnet and firewall are the boundary. The passphrase is still enforced when set, and still required for `0.0.0.0` / `::` and global addresses. `install.sh --systemd` applies the same rule
- `sandbox/proxmox/50-firewall.sh` rewrites only its own tenant's sections of `cluster.fw` and adds a `-ctl` group for the control plane; VMs are selected by pool membership
- `glue/bin/dispatch` counts lent VMs from the sandbox state file instead of parsing VM names (names now differ per tenant)
- `workflow/bin/run` honors `SANDBOX_STATE`, `SB_KEY` and `SB_JUMP` for its scp calls

### Fixed
- `31-provision-base.sh` creates the `dev` database (the psql check at the end failed on a fresh base template); `40-pool.sh` no longer aborts on the first pool of a project under `pipefail`; `20-gateway-lxc.sh` starts the CT before appending keys (a freshly created gateway stayed stopped)

## [0.2.0] - 2026-09-06

### Added
- `~/.config/aifactory/workspace` (one line, a path) as a second way to point at the workspace; `AIFACTORY_WORKSPACE` still wins. Works for processes that do not go through a shell. `paths.describe()` reports `workspace_source`
- Getting-started guide: how to reproduce the setup on another machine (two clones, secrets entered by hand)
- Leak guards: `.githooks/` (pre-commit on staged changes, pre-push with gitleaks) installed by `bin/install-hooks.sh`; `bin/oss-check.sh --staged`; a `secrets` CI job (gitleaks over full history); GitHub secret scanning and push protection enabled
- `examples/projects/aifactory/`: aifactory as its own sandbox project (public, tokenless clone, `mkdocs serve` on :3000 as the app, gates = CI set + `bin/oss-check.sh`). Anyone can run a ticket end to end with it; the maintainers use it for dogfooding
- `console/bin/install.sh --launchd` bakes `AIFACTORY_WORKSPACE` into the plist, so a workspace outside the repository also works for the resident console

### Fixed
- Runner: when the wip-branch push fails (for example the GitHub App lacks a permission), the diff is saved to `wip.patch` in the run directory instead of being lost with the VM rollback
- GitHub App manifest now requests `workflows: write`, and `sandbox` includes it when issuing installation tokens; without it GitHub rejects pushes that touch `.github/workflows/`
- `console/bin/install.sh`: a fullwidth parenthesis right after `$ws` was parsed as part of the variable name
- CI: the `bash -n` loop used `bash -n "$f" && echo ok`, so a syntax error in any file but the last one left the step green; it now fails on the first bad file and also checks `console/bin/install.sh`. The gate list lives in `examples/projects/aifactory/gates.sh` alone — it gained the `paths` check and `provision.sh` calls it instead of keeping its own shorter list

## [0.1.0] - 2026-09-06

First tagged version. The repository history starts here; earlier internal history was not carried over because it contained private project records.

### Added
- `lib/aifactory_paths.py`: one place that decides where operational data lives (`AIFACTORY_WORKSPACE`, default `workspace/`, git-ignored). `kb`, `run`, `intake`, `dispatch`, the console and the MCP server all use it (ADR-0016)
- `examples/projects/kumitate/`: a shipped reference project definition (`project.yml` / `provision.sh` / `gates.sh`)
- `bin/migrate-workspace.sh`: one-shot migration from the old in-repo layout
- Apache-2.0 license, `CONTRIBUTING.md`, `SECURITY.md`, `CODE_OF_CONDUCT.md`, GitHub issue / PR templates, CI (`.github/workflows/ci.yml`)
- English `README.md` (Japanese in `README.ja.md`)

### Changed
- `sandbox/bin/sandbox`: `PVE_HOST` and `GW_SSH` no longer have built-in defaults; set them in `~/.config/sandbox/env`. New `SB_POOL_NET` / `SB_POOL_BASE`
- `sandbox/proxmox/*.sh`: node name, subnet prefix and VMID bases come from `SB_NODE` / `SB_NET` / `SB_GW_CT` / `SB_BASE_VMID` / `SB_POOL_BASE` (defaults unchanged)
- The kanban `run` column stores the run directory name instead of `workflow/runs/<name>` (old values are still resolved)
